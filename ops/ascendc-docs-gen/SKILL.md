# Ascend C 算子文档生成

## 核心原则

算子文档是开发者资料与源码证据的结构化重组。开发者提供的算子规格、需求和设计文档用于确认目标与设计意图，源码用于核验实际实现。参数、数据类型、格式、shape、平台支持、约束、确定性行为和错误码必须有证据；不得凭空编造。

## 资料来源与冲突处理说明

解释 aclnn 文档或 README 的所需资料、生成依据或资料—源码冲突处理方法时，**先说明以下两条来源路径，再说明本次采用的事实与缺口**：

1. **未提供任何规格、需求或设计文档时，直接依据源码生成。**
2. **提供了规格、需求或设计文档时，先完整读取已提供的资料并提取设计意图，再完整扫描源码核验实际实现；不得只选其中一类输入。**

开发者资料是可选输入，不是源码生成的前置门槛。不能仅以“资料可选”或当前分支代替完整来源说明。已声明提供但不可读的资料仍是未解决输入，不能作为“未提供”跳过。这些方法说明不写入正式 API 文档或 README 正文，也不扩展到与来源无关的局部咨询。

## 本轮动作与说明范围

资料来源、章节和流程等写作咨询，在完整读取适用规范后解释所问规则的技术含义、适用条件及条件变化后的处理，不仅罗列标题或给出本次“可以/不可以生成”的结论。具体要求仍以本 Skill 的来源策略、权威模板和取证指南为准，不另立成品格式。

所问规则已能依据用户给定事实和 Skill 规范解释，且未要求读取或核验具体输入时，不检查或搜索算子目录、工作区、仓库、输入附件或其他 Skill 来验证题设，也不运行生成工具或创建完整会话。用户已说明源码不可访问时，按这一前提解释核验计划和交付边界，不搜索后将其改判为“缺失”；参考资料中的路径只是方法示例，不是本次源码位置。

用户未声明提供源码且实际目录未知时，请求实际路径并说明不依赖源码即可回答的规则；已声明提供时，按后文区分输入声明与可读性。用户要求生成、修改、读取或核验具体文件时，继续执行相应任务，确认实际路径并读取目标；同时要求说明计划不能将执行请求改为纯咨询。输入不足只暂停受阻部分，不虚报已完成。

## 开工前：先读写作规范，再查算子事实

生成、更新或说明 aclnn 接口文档和 README 的写作流程时，先实际完整读取本次所需的以下参考资料，再回答流程或进入源码提取；列出待读清单不等于完成这一步。相对路径均以本 Skill 目录为基准，不是算子源码目录：

| 任务 | 开始写之前完整读取的参考文件 |
|------|---------------------------|
| aclnn 文档或 README | [source-extraction-guide.md](references/source-extraction-guide.md)：字段提取、证据优先级与核验规则 |
| aclnn 文档 | [aclnn-api-doc-template.md](references/aclnn-api-doc-template.md) 和 [example-aclnn-md.md](references/example-aclnn-md.md)：权威模板与完整成品示例 |
| 算子 README | [operator-readme-template.md](references/operator-readme-template.md) 和 [example-readme.md](references/example-readme.md)：权威模板与完整成品示例 |

同时生成 aclnn 文档和 README 时，先完整读取上表全部五个文件，再扫描算子源码；只生成其中一种时，读取指南及该类型的模板和示例。`grep` 章节标题或只读开头不能代替完整阅读，长文件分段读取到末尾。需求分析、详细设计和迭代计划仍按各自模板处理，不额外读取无关参考。

回答“开始写之前检查哪些文件、如何保证不编造”等流程问题时，按指南的[证据文件覆盖](references/source-extraction-guide.md#证据文件覆盖)说明各类文件及核验用途，再说明事实表、独立文档与 README 全入口、交付核对的完整链路。Tiling 头文件、Tiling 实现和 Kernel 不因合并清单而省略。事实表须把签名参数、dtype/format/ParamType、平台分支和约束逐项绑定到源码位置及核验状态，不能只列源文件后直接跳到生成。交付核对同时覆盖接口数量、签名参数、类型/格式、平台、约束，以及相对链接、样例路径和前向算子引用；源码不可访问时将这些列为后续核验计划，不能声称已完成。文档示例只用于学习结构和格式，不能作为目标算子的参数或平台支持证据。

提供的源码路径不存在或不可读时，只阻塞算子事实核验，不阻塞 Skill 写作规范的读取。即使用户只要核验计划、不要求生成文档，也必须在本轮答复前完成适用参考资料的完整读取；同时涉及 aclnn 文档和 README 时就是上表全部五个文件，不能把可读的模板和示例留到取得源码之后。长文件按连续范围读取至末尾，不能只读指南就转去探索其他 Skill。

已完整读取的文件才能标为“已读取”；参考文件缺失、权限不足或读取失败时说明路径、原因和影响，不虚报完成。同一上下文中已完整读取且未变化的参考无需反复读取。源码缺失时说明待核验计划并请求正确目录，不宣称源码已核验或文档已交付，也不用其他算子源码替代。

## 先判断输入类型

| 输入 | 处理方式 |
|------|----------|
| 同时提供算子规格、需求或设计文档和可读源码目录 | 先完整读取已提供的开发者资料，提取设计意图，再完整扫描源码核验当前实现；结合两类证据按请求生成 aclnn 文档或 README，不得只选其中一类输入 |
| 只提供可读源码目录，未提供任何规格、需求或设计文档 | 直接依据源码按请求生成 aclnn 文档或 README，不要求补交这些可选资料 |
| 要求生成需求分析、详细设计或迭代计划 | 按开发者给定信息和对应模板生成，保留原有文档能力 |
| 提供已确认规格，但源码暂时不可用 | 用户要求草拟时按同一模板生成草稿，所有未经源码核验的字段标注“待确认”，并说明缺失证据 |
| 既无可读源码，也无已确认规格 | 请求实际源码目录或必要规格，只交付流程和缺失输入说明，不补造算子事实 |

用户是否声明提供资料或源码，与当前是否能定位、读取这些输入分别记录。已声明提供但无法读取的输入是未解决输入，实际生成或核验时记录缺项及影响并请求可读路径，不能改判为“未提供”。只解释方法时，按用户给定的输入状态说明资料读取、源码核验及对照方式，不以本轮尚未取得具体路径否定题设或推迟方法说明；实际读取前再确认可读位置，不能把题设当成本轮已完成的文件核验。资料可选不等于可以忽略已提供的资料。

读取资料在先不代表其覆盖源码事实；来源策略说明先读什么，后文的证据优先级决定冲突时采用什么。无资料直接依据源码也不等于缺源码时可以补造结论。

资料与源码不一致时，默认以已核验源码描述当前实现，在交付说明中保留资料预期、双方证据和待确认问题。**当前采用值与冲突原因分开判断**：请开发者确认是源码未实现或实现有偏差，还是规格、需求或设计文档未同步；不一致本身不能证明哪一方需要修改，未确认前不得断言“设计目标尚未实现”或直接要求变更实现。

## 支持的文档

| 文档类型 | 输出位置 | 模板 |
|---------|---------|------|
| 需求分析 | `operators/{operator_name}/docs/REQUIREMENTS.md` | [requirement-analysis-template.md](references/requirement-analysis-template.md) |
| 详细设计 | `operators/{operator_name}/docs/DESIGN.md` | [detailed-design-template.md](references/detailed-design-template.md) |
| 迭代计划 | `operators/{operator_name}/docs/PLAN.md` | [iteration-plan-template.md](references/iteration-plan-template.md) |
| aclnn 接口文档 | `<算子目录>/docs/aclnn{ApiName}.md` | [aclnn-api-doc-template.md](references/aclnn-api-doc-template.md) |
| 算子 README | `<算子目录>/README.md`，如 `operators/exp/README.md`（算子根目录） | [operator-readme-template.md](references/operator-readme-template.md) |

每种文档只使用表中的唯一权威模板；“是否提供开发者资料”只改变信息提取和核验方式，不改变模板。资料用途和冲突处理统一遵循前述来源策略，不静默丢弃任何一方。

## 源码驱动生成

### 1. 读取规则与发现接口

先完成“开工前”参考资料读取；该步骤不因缺少算子源码而省略。随后处理开发者资料和源码证据。

如果开发者提供了算子规格、需求分析、详细设计或既有接口文档，先完整读取并提取预期功能、接口、平台、约束和设计决策，建立带资料来源的“设计意图”清单，再完整扫描源码逐项核验。没有任何规格、需求或设计文档时，直接进入源码提取流程；不得因为已有资料而跳过源码分析。

实际新建或重新生成完整 ACLNN API 文档时，由主 Agent 使用 [完整生成流程](references/aclnn-full-api-docs-gen/WORKFLOW.md)，命令以模块目录为根。将资料状态、来源定位和设计意图交给模块，在其输入确认关口处理缺项，不先扩大范围搜索源码。模块负责预处理、阶段依赖、候选审阅及交付；本节的证据优先级、权威模板和 README 全入口约定继续适用。局部修订和其他文档不以完整生成会话为前提。

按已完整读取的源码提取指南，递归扫描 `op_host/op_api/aclnn_*.h` 中的全部 `ACLNN_API` 声明，不得只按文件名推断接口数量；多个接口可能共用一个头文件或实现文件。

同时检查 `examples/test_aclnn_*.cpp` 和 `tests/st/`，为每个接口建立独立清单。一个算子有多个 aclnn 接口时，每个接口必须生成独立文档，并在算子 README 的调用说明中逐一列出全部 aclnn 入口及对应文档/样例链接；单个接口的平台差异或废弃状态不能使其他入口从 README 消失。回答多接口文档如何组织的咨询时，也要同时说明独立 API 文档和 README 全入口清单这两项交付。

### 2. 完整读取证据文件

按指南的[证据文件覆盖](references/source-extraction-guide.md#证据文件覆盖)逐类确定目标源码，在可用范围内完整读取，不得只看命中行。按实际调用链覆盖共享文件及必要依赖；不能把预处理首轮清单当作完整证据范围。缺少文件时记录缺失项和影响，不得把常见实现当作当前算子的事实。

### 3. 建立结构化事实表

生成独立文档前，先为每个 aclnn 接口建立结构化事实表，每项记录结论、源码文件/位置、核验状态及冲突或缺失证据，分别整理：

- 两段式函数签名、参数顺序和空指针语义
- 输入、输出、属性的 ParamType、类型、格式、shape、连续性要求
- 平台支持、接口废弃状态及替代接口
- 通用约束、平台差异化约束、条件输出和 shape 推导
- 确定性行为、隐式 Cast 和可能的精度损失
- 错误码及对应的源码校验分支；注册类型本身不能证明运行时拦截或具体错误码
- 示例文件、公式和 README 调用入口

证据优先级：实际 aclnn 接口及校验逻辑 > tiling 参数校验 > def/infershape 定义 > 注释和示例。发生冲突时在交付说明中列出文件位置和采用理由。

如果存在开发者资料，再建立“资料—源码对照表”，至少记录：资料结论、源码结论、证据位置、一致性状态、最终采用值和待确认事项。未被源码证实的能力不写成当前已经支持；冲突原因按前述策略交开发者确认，不从文档采用值反推。

### 4. 生成 aclnn 文档

使用开工前已完整读取的 aclnn 权威模板和成品示例。每个接口生成一个 `docs/aclnn{ApiName}.md`，章节顺序、参数表列、产品 `<term>` 标签、返回码链接和两段式调用示例严格遵循模板。

aclnn 写作咨询也须给出路径规则和信息边界：输出到`<实际算子目录>/docs/aclnn{ApiName}.md`；例如目录为`operators/layernorm`时，输出为`operators/layernorm/docs/aclnnLayerNorm.md`，实际目录名须确认，不把示例路径当成已存在的源码路径。说明两段式声明、产品支持情况、功能说明、函数原型、8字段参数表、返回值、按平台描述的约束与确定性行为及调用示例；缺少源码时只能依据已确认规格草拟并标注“待确认”，只要求咨询时不生成文档。

产品名和格式遵循 [ops-transformer Wiki](https://gitcode.com/cann/ops-transformer/wiki) 的 aclnn API 文档模板：产品支持情况使用无序列表，每项用 `<term>` 和配对的 `npu` 注释标签标记。产品支持、默认确定性行为、是否支持切换是独立事实，分别按平台核验 config、AddConfig、接口和 Tiling/Kernel 实现；缺证时保持“待确认”，不能由模板示例推断。已确认支持手动开启时配置接口写 `aclrtSetSysParamOpt`，但这不证明默认非确定性。反向算子引用经核验的前向文档；接口废弃仅影响相应接口，不扩大为整个算子不支持该平台。

### 5. 生成算子 README

使用开工前已完整读取的 README 权威模板和成品示例。README 内容以已核验源码为当前实现的事实依据，结合已提供的规格说明、需求分析（`REQUIREMENTS.md`）和详细设计（`DESIGN.md`）说明功能目标与设计意图。解释写作所需资料时，将这些开发者资料与 Skill 内规范格式的模板、示例区分，不能互相替代；资料可选性与冲突处理遵循前述统一来源策略。README 参数分类以 `*_def.cpp` 的 Input/Output/Attr 为准，并列出该算子的全部 aclnn 调用入口。

README 写在算子根目录：`<算子目录>/README.md`；例如 Exp 算子为 `operators/exp/README.md`，已有分类目录时使用 `{op_class}/exp/README.md`。缺少源码时，只能依据已确认资料草拟，所有未经源码核验的字段标注“待确认”，不能仅在资料与源码冲突时才标注。

README 核心章节为产品支持情况表、功能说明（含适用的计算公式）、5 列参数说明表、可选的约束说明、调用说明和可选的参考资源。Wiki 允许按实际需要增加自定义章节，避免重复；函数原型、返回值和完整调用代码放在对应 API 文档中。

回答“README 需要哪些资料、包含哪些章节”等写作咨询时，也应说明上述输出路径、源码事实来源和缺少源码时的“待确认”规则，而不只罗列章节。

### 6. 交付前校验

- 确认本次所需指南、模板和文档示例均已完整读取；缺失资料和未执行的核验如实说明。
- 将所有接口声明、独立 API 文档和 README 调用入口三方逐一对账，确认无遗漏、无重复；多个入口共用样例时仍逐项列出入口，不以链接去重为由合并掉接口。
- 将函数原型参数顺序与参数表逐项对账。
- 将 dtype/format/ParamType 与 `*_def.cpp`、接口头文件逐项对账。
- 将平台和约束与 `AddConfig`、config 目录及 tiling 分支逐项对账。
- 校验文档中的相对链接、示例路径和前向算子引用。
- 对无法确认的信息标注“待确认”并说明缺失证据，不得用推测填充。

## 规格驱动生成

需求分析、详细设计和迭代计划按对应模板生成。需求分析评审确认后锁定，再据此完成并确认详细设计，详细设计确认后再制定 PLAN。变更先明确影响和方案，经确认后更新需求，重新确认后同步设计，并检查 PLAN、aclnn 接口文档和 README 的受影响部分。用户已明确授权的方案按授权执行，不重复索取确认；尚未确定的参数默认值或实现方案不自行补入。

若开发者提供规格、需求或设计文档以及源码，生成 aclnn 文档和 README 时必须同时使用两者：先完整读取资料提取设计意图，再完整扫描源码核验，最后输出当前实现文档和冲突清单。若没有提供这些资料，则直接依据源码生成；资料已声明提供但不可读时，记录缺项并请求可读路径，不能作为“无资料”跳过。

各文档修订记录包含版本、修订内容、时间和修改人。aclnn 文档从需求中的算子规格、API 定义和约束提取设计意图，README 综合需求、设计和代码；两者仍按本节之前的统一输入策略核验，不把新增需求写成已经实现。

取得此前缺少的源码后，重新核验草稿并替换待确认字段。

## 禁止事项

- 不得遗漏同一算子中的其他 aclnn 接口、OPTIONAL 参数或条件输出。
- 不得在开发者提供需求或设计文档时只读取源码，也不得因为已有文档而跳过源码核验。
- 不得从算子名称猜测数据类型、shape、平台支持或约束。
- 不得忽略平台分支、接口废弃信息、隐式 Cast、溢出和 NaN/Inf 等隐性约束。
- 不得在 aclnn 参数表中省略类型、留空“使用说明”列，或把内部枚举原样写给用户。
- 不得在 README 参数名中附加 C/C++ 类型。
