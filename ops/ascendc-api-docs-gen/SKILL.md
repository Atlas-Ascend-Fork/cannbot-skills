# Ascend C API文档写作指南

## 概述

本技能提供Ascend C API文档的写作标准和模板参考。

## 先确定本轮交付

- **只询问规则、处理方式或局部修订范围**：依据已给出的事实说明本次影响范围、保留内容和必要前提，不生成文件或启动完整生成会话。信息足够说明范围时直接回答，无需先定位原文档、发现代码仓或查找清单；实际编辑文件时再取得目标路径并读取原文。
- **用户说明已有清单不存在或不可读**：说明完整生成当前无法继续，请提供可读的 `manifest.json` 路径，然后暂停。不自动搜索替代清单、接口或代码仓，也不改为创建新清单；收到可读路径后先读取指定清单，再按其中的目标和来源继续。用户明确选择另建会话时，再按新会话所需输入处理，保留原记录。
- **实际新建或重新生成完整文档**：按下一节处理输入。完全未提供清单与已有清单不可读是不同状态，不能因当前没有可读清单就一律进入创建流程。

用户同时明确要求生成或修改文件时，说明检查计划后继续相应任务；只有用户限定本轮先说明时才停在说明。输入不足时按对应流程请求缺项，不把原生成请求改称为纯咨询或声称已完成。

## 写作规范咨询

章节顺序和具体格式见 [写作规范导航](references/README.md)。仅阅读与问题相关的写作规则，不为咨询创建清单或执行生成阶段；说明章节要求时先解释技术内容和证据边界，再补充格式：

- 功能、原型、参数、返回值、约束及示例均须来自适用版本的头文件、可达实现和已核验资料；不能臆造 API 行为。实际涉及的类型、对齐、平台限制和调用约定据证据说明，不要求所有 API 具有 Tensor 对象。
- 产品列表明确列出支持范围；未核验的产品不得标注支持，也不能因未找到证据就标为不支持。咨询时说明核验要求和缺证处理，实际生成时才按完整流程补证或确认；格式示例本身不证明支持状态。
- 返回值说明应解释实际返回值的含义，以及有证据且适用的错误返回或异常行为；不为所有 API 假设错误码或异常。void 的返回值章节仍按规范写“无”，相关错误行为有证据时写在适用的约束中。

## 完整生成

用户实际要求新建或重新生成完整 API 文档时，由主 Agent 进入 [完整生成流程](references/ascendc-full-api-docs-gen/WORKFLOW.md)，先核对清单输入：未提供 manifest 的任务从流程中的会话创建任务开始，收集必要输入并创建清单；已提供 manifest 的任务核对已有清单。命令以该模块目录为根。

局部修订和咨询不以完整生成会话或其检查工具为前提；局部修订保留未受影响内容，技术结论仍须有依据。不能把用户给定的已确认事实表述为本轮已经完成源码核验。
