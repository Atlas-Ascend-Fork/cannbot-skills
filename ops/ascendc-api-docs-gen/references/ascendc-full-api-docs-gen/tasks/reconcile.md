# 事实对齐、资料触发回查与用户确认

## 目标与进入条件

先判断每份已提供资料与当前 API 的关系，再按关系分别处理：当前 API 资料用于事实对齐；同类 API 资料只可作为调用示例结构参考；代码可达的下层 API 资料逐条判断是否适用于当前 API。产出资料事实索引、资料触发的代码回查记录、实际冲突清单和可用于生成的规范事实。

进入本任务前，`code-evidence.md` 必须已覆盖本次全部成员并对应当前 `manifest.json`。先完整读取这两个文件；不满足时返回 `tasks/evidence.md`，不得打开任何资料文件。资料状态不是 `provided` 或 `absent`、或“其他资料已收集完毕”尚未确认时，返回技能入口处理，不能自行假定缺失资料不存在。

资料不是用来填满首轮代码遗漏的答案库。严格按以下顺序处理：

1. 判断每份已提供资料主要描述当前 API、多个 API、同类 API、代码可达的下层 API 还是其他 API；
2. 把当前 API 或混合资料中明确属于当前 API 的章节解析为 R-ID；把下层 API 资料解析为 D-ID，但不能直接当作当前 API 事实；同类 API 资料不解析技术事实；
3. 把 R-ID 与相同事实槽位、相同适用范围的代码事实匹配；D-ID 先逐条判断当前 API 是否实际使用其行为；
4. 对尚无充分代码事实的候选，先执行资料触发的定向代码回查；
5. 用补充后的代码事实重新比较，再判定实际冲突；
6. 只把仍需裁定的事实交给用户确认。

因此，一份或多份资料共同写了同一个事实、而首轮 `code-evidence.md` 没有记录时，不能跳过代码回查。回查发现代码也支持该事实，就补入 K-ID，并把全部来源作为一致事实处理，不向用户提出无意义的问题。

若没有任何 `provided` 资料，跳过资料解析和资料触发回查，继续后续阶段；不得因为资料不存在创建问题。

## 资料对应 API 的判定

在提取任何 R-ID 前，对每份状态为 `provided` 的资料读取标题、函数原型、代码块、明确列出的 API 名称、调用约定和成员名称，并与 `manifest.json` 的 `documentApiName`、`targetApi.members`、`apiType`、`callingConvention` 比较。文件名、目录名或“同属某类 API”不能单独作为依据。

将结果写回该资料的 `documentTarget`，使用 `tools/ascendc-record-reference.mjs --document-target ...`；资料路径被替换后会自动回到 `unclassified`，必须重新判定。`peer-api` 和 `downstream-api` 都必须记录检测到的 API 名称及判定依据。每份资料都写入以下一种结论：

- `current-api`：标题、原型或明确章节匹配当前 API 或已选成员，正常提取事实。
- `mixed-api`：同一资料同时覆盖当前 API 和其他 API；只提取明确属于当前 API 或已选成员的章节，其余内容不进入 R-ID。
- `other-api`：资料明确描述其他 API，且不是同类 API 或代码可达的下层 API；记录为 `comparison-only`，可参考章节组织或措辞，但原型、参数、产品支持、约束、公式和调用示例都不能成为当前 API 的候选事实、代码搜索锚点或最终文档内容。
- `peer-api`：资料明确描述与当前 API 同一 API 类别的另一接口。它只可作为调用示例的工程结构、变量组织、Host/Kernel/CMake 组织方式参考；其中任何 API 原型、参数、约束、输入值、结果或技术结论都不能成为当前 API 事实。
- `downstream-api`：资料明确描述临时调用关系定位结果中可达的下层 API。先记录与当前成员、条件和调用位置的关联；只在“下层资料适用性”逐条确认后，才可影响当前 API 文档。
- `excluded`：用户明确要求不使用；不提取事实，不参与对齐。
- `needs-confirmation`：资料没有足够身份信息，或用户声明它适用于当前 API、但标题/原型显示为其他 API；先提问，不能提取事实。

`other-api` 的资料不因“同类接口”而自动产生 S-ID 或 C-ID。只有资料中明确列出当前 API 的章节，或用户明确指定了可用于当前 API 的章节/事实，并且这些内容随后完成当前 API 直接代码链回查，才可作为候选事实。

在 `reference-evidence.md` 开头始终先写入资料适用性表：

```md
## 资料适用性
| 资料 | 检测到的 API | 判定 | 使用方式 | 原因 |
|---|---|---|---|---|
| <资料名称>《<文件名>》 | <API 列表或未识别> | current-api / mixed-api / peer-api / downstream-api / other-api / excluded | facts / selected-sections-only / example-template / dependency-evidence / comparison-only / excluded | <标题、原型、调用关系或用户确认依据> |
```

对 `needs-confirmation` 的资料，先用 `question` 询问用户：默认选项为“仅作同类接口参考”和“不使用该资料”；用户若选择 `Other / 自行输入` 声明部分内容适用于当前 API，必须再询问其具体章节或事实，再将这些范围按 `mixed-api` 记录。用户确认“仅作同类接口参考”后写入 `other-api`；确认“不使用”后写入 `excluded`。每次写回后重新读取 `manifest.json`，再继续处理下一份资料。

## 调用示例的资料回退

仅当 `code-evidence.md` 已记录某成员在代码仓 `examples/` 中没有可用示例（包括确定性 `Compute()` / `Process()` 结果及可用的 Helper 调用链或 Helper 片段）时，才在资料阶段寻找补充样例。先完成所有资料的 API 判定；可检查的只有 `current-api` 资料，以及 `mixed-api` 中明确属于当前 API 或已选成员的章节。它包括内部脱敏资料、仓内人工文档和任意额外资料，不按资料名称区别。

资料中的示例只有同时满足下列条件才可采用：

- 示例代码或其明确标注的片段实际调用当前 API 或当前成员，不能仅因资料标题相同而采用；
- 调用的成员、参数个数、顺序和调用方式与本次精确原型一致；输入、结果、初始化和约束仍须逐项回到当前 API 的 K-ID、R-ID 或已确认事实，不能把未证实的示例文字直接复制；
- 在 `reference-evidence.md` 记录资料名称、完整路径、章节/行范围、所覆盖成员和核验结果；示例中出现的新前提或行为仍按资料事实触发代码回查。

不得从 `peer-api`、`downstream-api`、`other-api` 或 `excluded` 资料中提取当前 API 的调用、输入或结果。若当前 API 资料也没有可用示例，只能以当前 API 的精确原型、当前 API 可达实现和已冻结事实构造示例；可最多借用一份 `peer-api` 资料的工程、Host、Kernel 或 CMake 组织方式，不能借用其 API 调用、参数、输入值、结果或行为。

按每个成员在 `resolution.md` 的“调用示例组成依据”表先写一行“示例来源”：`代码仓 examples`、`当前 API 资料` 或 `当前 API 实现与同类 API 结构`。这行要同时写明真实文件或资料定位以及 K-ID/R-ID；不能跳过前一优先级而直接使用后一项。
## 资料事实解析

完成资料对应 API 的判定后，只对 `current-api` 资料和 `mixed-api` 中明确属于当前 API 的章节，逐份完整读取并按与代码事实相同的原子槽位提取 R-ID。对 `downstream-api` 资料逐份完整读取并提取 D-ID，但 D-ID 只能进入“下层资料适用性”表，不能与当前 API 的 R-ID 混合。`peer-api`、`other-api` 和 `excluded` 不提取技术事实：

- 成员/overload 原型和调用约定；
- 产品支持、dtype、功能、公式及适用条件；
- 每个模板参数、形式参数、结构体字段和枚举的语义、默认值、范围、单位、支持取值和配置要求；
- 返回值、单参数约束、多参数组合、输出初始化、状态影响、示例和术语。

当前 API 资料的每条资料事实必须使用全局唯一的 `R-xxx` 编号，并记录资料名称、资料 ID、文件名、完整路径、标题/表格/行范围、原文必要摘录、归一后的候选值、事实槽位和适用范围。下层 API 资料使用全局唯一的 `D-xxx` 编号，除上述定位外还必须记录下层 API 名称、关联的调用关系编号、当前成员、条件和调用位置。适用范围至少包含可辨识的成员、overload、产品和条件；资料没有说明范围时写“范围未说明”，不得自行扩展。

即使多份资料表述相同，也必须分别原子化，各自保留原文摘录和定位；不得以“同另一条事实一致”代替来源证据。允许归一空白、列表顺序、等价产品别名和纯格式差异；不得将范围、单位、默认值、方向、产品、参数含义、支持取值、公式变量或适用条件的差异归一掉。资料未提及是覆盖缺口，不是冲突。

`absent` 资料不建章节；`provided` 资料数量为零，或全部资料均为 `other-api`/`excluded` 时，写明“未提供可用于当前 API 的解析资料”。

## 下层 API 资料的逐条适用性

对每条 `D-xxx`，先读取临时调用关系定位结果与 `code-evidence.md`，把它关联到当前成员、调用条件、调用位置和真实下层 API。下层资料中写有约束、数据类型、特殊值、地址要求或结果行为，不等于当前 API 对用户承诺同一结论。

逐条执行以下判断：

1. 当前成员是否在相同条件下实际调用该下层 API，或经宏表函数映射到它；
2. 当前 API 是否将该下层行为暴露给用户，而不是在 wrapper、转换、校验或固定配置中改变、屏蔽或限制它；
3. 代码是否能证明该事实对当前 API 的适用成员、产品、数据类型和参数组合。

每条 `D-xxx` 必须在 `resolution.md` 的“下层资料适用性”表中有一行。处理只能是：`写入当前 API 文档`、`不写入当前 API 文档`、`仅作为实现说明`、`经用户确认写入当前 API 文档`、`用户明确暂缓`或`不适用`。前两项以外的写入结论必须有 K-ID 或用户确认的 C-ID/S-ID；不能仅因下层文档存在或调用关系可达而写入。

代码无法判断当前 API 是否使用某项下层行为时，必须用 `question` 询问用户是否将该项作为当前 API 的对外约束保留，或暂缓；问题中要同时列出下层资料名称、文件名、完整路径和 D-ID，以及当前成员、条件、调用位置和代码无法确认的原因。没有用户确认时不得写入。

每条准备写入最终 API 文档的 wrapper 事实，都要与 `code-evidence.md` 的“对外事实候选”逐条映射。映射必须保留适用范围、来源层与透传关系、正文位置和必含标识符；不能因为正文组织变化而遗漏已证实的 mask 传播、返回状态、默认值或 wrapper 限制。测试覆盖、构建、编译、运行和验证状态不得进入映射或最终 API 文档。

## 资料触发的代码回查

在开始冲突判定前，只为已生成 R-ID 的当前 API 资料候选寻找相同事实槽位且适用范围相同的 K-ID。下列情形均须回查：

- 没有对应 K-ID；
- K-ID 只记录了更宽或更窄的成员、overload、产品或条件，不能覆盖资料断言；
- K-ID 的证据状态为“缺口”或“需开发确认”；
- 资料提出了首轮未列出的结构体字段、枚举取值、组合约束、输出状态、示例前提或语义关系。

同一归一事实被任意数量资料重复陈述时，只建立一条回查记录，并关联全部相关 R-ID；不要因来源数量增加而重复扫描代码。

### 回查方法

以资料事实的成员、形参/字段、产品、数值、单位、枚举值、公式符号、术语和资料中的代码定位为搜索锚点，但只在目标 API 的直接代码链内核验。每次回查先按 `tasks/evidence.md` 作分工判断；在 `code-evidence.md` 的“代码阅读分工”新增回查批次，全文搜索使用受限代码搜索工具。完整遵守该任务的代码范围、来源优先级、有效代码链路、语义旁路追踪、组合约束和不可推断规则：

1. 回读成员公开声明、注释、同一原型的参数/模板定义和直接公共头；
2. 沿正式参数或字段的真实传播位置读取 wrapper、实现、check、tiling、host 校验和最终调用；
3. 必要时补入直接可达的基础 API 实现、结构体/枚举定义或示例，并记录进入原因；
4. 只能用完整符号和同一实参位置建立旁路语义；资料概念与代码名称不同，不得按名称相似猜测；
5. 可证实事实追加为新的 K-ID，写入文件、符号、行号、适用范围和“提取方式：资料触发回查”；无法证实则追加代码缺口，写明已查范围和未能建立的环节。

不得为回查扫描无关目录、其他 API 或相近接口；也不得把资料语句当作代码证据写入 K-ID。

### 回查结果分流

- **代码支持候选**：把新 K-ID 与相关 R-ID 写入 `resolution.md` 的已确认事实，决策方式为“代码已证实（资料触发回查）”；无需提问。
- **代码只支持部分范围**：按成员、overload、产品或条件拆分；资料扩大或未说明的部分继续进入对齐，不能被已支持部分代替。
- **代码给出不同值、否定或不兼容范围**：形成实际冲突，进入用户确认。
- **完成规定回查后仍无可读代码证据**：保留为“已回查未证实”的资料事实。若它会进入最终文档，用 `question` 让用户选择保留或暂缓；来源数量或来源一致性都不能自动采纳或否定。

在完成回查前不得发起冲突选择问题。

## 冲突判定

按“事实槽位 + 适用范围”建立候选集合，再比较代码候选和全部 R-ID：

- 多个来源给出相同、且代码已证实的候选：直接确认，不形成冲突；
- 多个资料来源给出相同候选、但代码回查仍未证实：建立一项 S-编号，询问是否保留这一共同事实或暂缓；
- 仅一个资料候选、代码回查仍未证实：建立 S-编号，询问是否保留该明确来源的事实或暂缓；
- 两个或以上候选给出不兼容值，或资料与可达代码的否定/不同断言冲突：建立 C-编号；
- 资料把不同成员、产品、overload 或参数组合混为结论且无法确定范围：建立 C-编号或拆分为多个 S-编号，取决于是否存在不兼容候选。

C-编号只用于实际存在不兼容候选的冲突。S-编号用于“已回查未证实、但可能保留”的资料事实，不计入 `unresolvedConflicts`。没有资料、没有实际冲突且没有需要保留的 S-项时，不发起问题。

每道问题只确认一个原子事实；相互独立的事实每批至多三个。只有不能被单独采用的同一参数组合可以放在同一道问题中。

## 必须使用 `question` 的确认流程

先完成“资料对应 API 的判定”中所有 `needs-confirmation` 项，再把全部 C-项写入“冲突清单”，把 S-项写入“待确认的资料补充事实”，状态均为待确认；再使用原生 `question` 工具逐项或每批至多三个相互独立项交互。没有需要裁定的事项时，不发起问题。

每个资料候选在问题和 `resolution.md` 中必须以以下格式显示，不能只说“资料记载”：

> `<资料名称>《<文件名>》`记载：<候选值>
> 定位：<完整路径>，<标题、表格或行范围>

同名文件或同名资料项仍须保留完整路径区分。完整路径只用于提问和内部决议记录，不能写入最终 API 文档。实际冲突的问题再列出代码候选（如有）、所有不兼容资料候选、各自完整定位和推荐项；选项只对应实际候选，且必须保留 `Other / 自行输入`。

共同但未证实的 S-项，选项为“保留以下资料共同记载的具体事实”和“暂缓”，并逐条列出每个来源；单一来源 S-项，选项为“保留 `<资料名称>《文件名》` 的具体事实”和“暂缓”。用户通过 `Other / 自行输入` 给出新文字或“暂缓”时，先归一为原子事实，再发起第二道 `question` 确认归一文本。

用户明确暂缓时，最终值为 `【待开发补齐】`，并保留缺口原因；代码冲突但用户未裁定时使用 `【需开发确认】`。没有 `question` 工具时，使用等价结构化提问或普通对话，完整展示同一问题的事实、来源和选项，取得明确回答并写入 `resolution.md`；不得从含糊回复推断确认。必需的 C-项或 S-项未获明确裁定时仍停在确认关口。

## 示例使用限制

对每个会因示例输入、参数组合、地址关系、状态或结果描述而被触发的未证实行为，在写入最终值时同时写入 `resolution.md` 的“示例使用限制”表。该表的“示例只能使用”是允许范围：只能依据已确认事实写出具体且安全的范围，不能用“正常值”“合适值”或“安全值”等模糊说法代替。

- `不得使用`写明未证实行为的触发条件；`校验写法`只列最终化工具可以直接拦截的代码字面量或表达式，每项使用反引号包围并以“、”分隔。无法静态匹配的条件写“人工审阅”，由生成和审阅规则逐项核对。
- 未证实行为不影响调用示例时，使用一行“全部成员 / 无 / 按已确认原型和事实 / 无 / 无 / 本次未发现会影响调用示例的未证实行为”。
- 若未证实行为会影响调用示例、但无法依据已确认事实给出允许范围，不得用任意数值或状态绕过；保持该槽位待补证，不能冻结或生成文档。
- 示例限制只约束本次 API 和已选成员，不能因同类 API、其他资料或相近实现而扩大或缩小。

## `resolution.md` 格式和状态

`resolution.md` 使用结构化 Markdown，而非独立 JSON。文件开头必须有：

```md
---
schemaVersion: 1
status: reconciling
manifestFingerprint: <从 manifest.json 复制>
unresolvedConflicts: <待确认的 C-项数量>
pendingReferenceApprovals: <待确认的 S-项数量>
---
```

每完成一道确认问题，都更新对应条目状态与两个数量。即使两个数量都为 0，本阶段仍保持 `status: reconciling`；只能由 `tasks/supplement.md` 在覆盖表完整后冻结。
