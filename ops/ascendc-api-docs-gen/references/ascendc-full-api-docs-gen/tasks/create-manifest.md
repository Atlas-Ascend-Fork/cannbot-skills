# 直接创建 manifest.json

## 适用范围

仅当用户尚无清单、需要新建完整生成会话时使用本说明。用户若明确给出 `manifest.json` 路径但该文件不可读，或已经说明已有清单不存在，报告问题、请求可读路径并暂停；不得自动转而创建新的 `manifest.json`，也不搜索替代清单或接口。不能将“已有清单不可读”当作“用户尚未提供清单”。用户明确选择另建会话后，重新核对新会话输入并保留原记录，不自动覆盖已有清单。

直接模式只依据用户指定的接口文件解析本次 API 及其应覆盖成员，不扫描代码仓的其他文件寻找候选接口。创建成功后，继续普通 `manifest.json` 流程；后续资料收集、代码取证、对齐、补证、生成和最终化规则完全不变。

## 收集最少信息

先检查用户消息。若以下信息已经明确给出，直接使用；只对缺少项调用 `question`：

> 请告诉我 asc-devkit 代码仓根目录、这次要写的 API 名称，以及声明或定义该 API 的接口文件路径。

用户可以用一句自然语言、列表或路径回答，不要求 JSON、命令行参数、成员函数列表或调用方式。接口文件必须在代码仓内；路径不存在、不是文件或位于仓外时，说明问题并仅追问该项。

缺少输入时，交接说明同时包含当前缺项和取得输入后的动作：信息齐备后，通过 `tools/ascendc-create-manifest.mjs` 创建标准 v2 `manifest.json`，读取新清单后继续完整流程。此时如实说明尚未创建清单，不把后续动作表述为已完成；取得回答后继续执行下节，不重复询问已提供项。提问工具不可用时使用普通对话完成同一交接。

## 创建 manifest.json

信息齐全后执行：

```text
node tools/ascendc-create-manifest.mjs --repo <代码仓根目录> --interface-file <接口文件路径> --api-name <API名称>
```

不得传 `--force`。工具只解析该接口文件，并根据函数声明之间的对应关系确定文档根和成员：同一公开接口的同步成员、`_padN` 变体以及源文件明确归组的成员会被纳入；无关的相近接口不会纳入。

工具成功后会在 `<代码仓>/outputs/<文档根 API>/manifest.json` 创建标准 v2 `manifest.json`。完整读取该文件，再回到 `WORKFLOW.md` 的资料收集步骤；不得自行补造或修改其中的 API、成员、调用方式或代码入口。

## 同名候选的确认

若工具报告同一 API 在该文件中有多个候选，先读取错误输出中的候选记录。每条记录包含候选 ID、API 类型、调用方式、成员和文件。必须调用 `question` 让用户选择，不得按名称、目录或多数成员猜测。

问题正文必须逐条显示候选的调用方式、成员和文件；选项对应实际候选。用户选定后，使用选中的候选 ID 重试：

```text
node tools/ascendc-create-manifest.mjs --repo <代码仓根目录> --interface-file <接口文件路径> --api-name <API名称> --selected-interface <候选 ID>
```

候选超过单次问题可展示的数量时，分批展示，并保留 `Other / 自行输入` 让用户填写候选 ID。指定 API 在接口文件中未找到时，报告工具列出的可识别 API，不扩大到其他文件搜索。

## 已有 manifest 的保护

若默认输出目录中已有内容不同的 `manifest.json`，工具会拒绝覆盖。告知用户已有 `manifest.json` 的路径；用户若希望继续，应以该路径重新进入普通流程。不得通过 `--force` 自动覆盖已有确认记录。
