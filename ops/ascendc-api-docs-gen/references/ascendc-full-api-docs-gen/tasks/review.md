# 最终文档审阅与冻结

先按 `references/api-scope.md` 判断规则适用范围。Tensor/TPosition、寄存器、线程或队列等字段仅在当前成员实际涉及时核验；不适用项明确记录“不适用”，不要求构造对应对象。Tensor 参数需要时再读取 `references/tensor-parameters.md`。

## 输入和边界

审阅 `tasks/generate.md` 在内存中形成的最终正文。只读取：

- `manifest.json`；
- `code-evidence.md`；
- `reference-evidence.md`；
- 已冻结的 `resolution.md`；
- 本次已核验的公开术语来源（如有）；没有对应来源时保持源码标识和准确含义，不加载历史词表作为规范。

审阅不是重新研究代码、重新选择来源或改写用户决策。若发现事实不完整、冲突、目标 API 信息不一致或需要补充代码，停止审阅并回到 `tasks/supplement.md`；若补证影响确认事实，必须回到 `tasks/reconcile.md` 的 `question` 关口。

不生成 `4_review.md`、校验报告或 diff。修正后的正文才是待写入的唯一最终文档。

## 必检项

### 1. 决议与输入有效性

- `resolution.md` front matter 必须为 `status: frozen`、`unresolvedConflicts: 0`、`pendingReferenceApprovals: 0`，且 `manifestFingerprint` 与 `manifest.json` 相同；“覆盖与待补证”表的每一行必须是终态，确保决议对应本次使用的 API、代码和资料。
- 每一项正文技术事实必须能回溯到 `resolution.md` 的最终值或 `code-evidence.md` 的精确原型；不能绕开已确认决议使用原始资料的表述。
- 检查 `reference-evidence.md` 的“资料适用性”表与 `resolution.md` 的“下层资料适用性”“调用示例组成依据”表：`other-api` 和 `excluded` 资料不得成为正文事实、函数原型、参数/约束、公式或调用示例的来源；`mixed-api` 资料只能使用明确属于当前 API 的 R-ID；`downstream-api` 资料只有逐条获准写入时才能影响当前 API 正文；`peer-api` 资料只能提供示例工程结构，不能成为 API 调用、参数、输入、结果或技术事实的来源。
- 已确认的自定义文字、`【待开发补齐】` 和 `【需开发确认】` 必须按决议保留。不能为了文档顺畅删除、降级或擅自补全。
- 核对 `code-evidence.md` 的“对外事实候选”与 `resolution.md` 的“对外事实映射”：每条写入正文的事实必须出现在指定章节并带齐必含标识符；正式 API 文档不得出现测试覆盖、构建、编译、运行、golden 或验证状态。
- 检测到“待确认”“需二次确认”、待代码补证、未完成的覆盖表，或本次使用的 API、代码、资料已经变化时，不得放行。
- 正文审阅通过后，必须先运行最终化工具的 --check 模式；预检失败时按错误回到正文、补证或确认关口，不得通过无关注释或包装代码规避校验。

### 2. 目标 API 信息与函数原型

- 标题、要覆盖的成员函数和调用约定必须与 `manifest.json` 完全一致。
- `函数原型` 必须包含 `code-evidence.md` 的全部精确签名；不能遗漏 overload、混入其它 API 或调用约定，也不能改写模板行、参数顺序和参数名。
- 每个声明独占一行并保留分号；函数原型章节不使用子标题或代表性压缩。
- 原型分组只能使用真实函数名或代码证实的用户可见模式，不能由参数集合、`sync` 后缀或模型猜测命名。

### 3. 产品、参数与约束

审阅时逐字比对以下固定产品块：

```text
<!-- npu="950" id1 -->
- Ascend 950PR&950DT系列产品：支持/不支持
<!-- end id1 -->
<!-- npu="A3" id2 -->
- Atlas A3系列产品：支持/不支持
<!-- end id2 -->
<!-- npu="910b" id3 -->
- Atlas A2系列产品：支持/不支持
<!-- end id3 -->
<!-- npu="310b" id4 -->
- Atlas 200I/500 A2推理产品：支持/不支持
<!-- end id4 -->
<!-- npu="310p" id5 -->
- Atlas推理系列产品AI Core：支持/不支持
<!-- end id5 -->
<!-- npu="310p" id6 -->
- Atlas推理系列产品Vector Core：支持/不支持
<!-- end id6 -->
<!-- npu="910" id7 -->
- Atlas训练系列产品：支持/不支持
<!-- end id7 -->
```


- 固定七项产品支持注释列表、顺序、`npu` 值和 `id` 必须原样存在；每项状态仅为“支持”或“不支持”，并与冻结事实一致。
- 表格必须覆盖每个形式参数和模板参数。方向、类型及适用的默认值、单位、范围、TPosition、产品限制和 overload 不得与原型或冻结事实冲突。
- 不同产品或 overload 的 dtype、参数组合和约束必须按事实完整区分；禁止并集、同上、增量描述或降低组合维度。
- 参数表中已完整表达的单参数约束不应在约束章节机械重复；跨参数组合和全局约束不得遗漏。
- 仅对实际 Tensor 参数：不把 `LocalTensor`/`GlobalTensor` 当成物理 Buffer，也不在缺少 TPosition 事实时伪造数据通路。

### 4. 功能、公式和示例

- 功能说明只描述用户可感知行为，不出现内部实现、路径或证据推理。
- 公式必须有已确认的用户可见关系；不得出现 intrinsic、helper、实现函数或未解释符号。含下标时必须有语义和范围。
- 调用示例必须覆盖要求覆盖的成员，且参数个数、类型、顺序与原型相符；不得有省略号、伪地址、未初始化地址空间指针或虚构的输出初始化。逐项核对“调用示例组成依据”的“示例来源”行：先核验代码仓 `examples/` 的当前成员 `Compute()`，再 `Process()`；若两者都不可用但 `code-evidence.md` 记录了按 `tasks/example-call-chain.md` 核验的 Helper 调用链或 Helper 片段，则核对候选文件、函数范围、调用边和目标 API 调用行。只有代码仓示例均不可用时才允许同 API 资料，仍没有时才允许当前 API 实现加同类 API 结构模板。同类 API 资料只能提供工程结构，不能沿用其 API 调用、参数、输入、结果或技术结论；下层 API、其他 API 和排除资料不能成为当前 API 调用示例来源。
- 逐行核对 `resolution.md` 的“示例使用限制”：代码、输入数据、参数组合、初始化方式和 `text` 结果均不得触及限制条件；结果不得描述未证实行为。不能仅因示例未出现某个明显字面量，就假定变量计算、地址关系或状态组合安全。
- 示例必须含“结果示例如下：”和 `text` 代码块，结果只能陈述可证明的事实。

### 5. 格式与对外边界

### 空章节格式

内容为空时，章节正文必须精确为单独一行“无”。特别是 `## 参数说明`、`## 返回值说明` 和 `## 约束说明`；禁止写成“无。”、列表项或附加解释。


- 标题和固定章节顺序正确；空的参数、返回值、约束章节只写“无”。
- 参数与约束使用简洁 Markdown 表格；正文中的标识符使用 `<code>...</code>`，而非 Markdown 行内反引号。
- 产品名按产品规范；其余术语只按本次已核验的公开来源统一。Tensor/TPosition/Buffer 的表述仅在适用时检查；未核验历史词表不作为修改依据。
- 全文不泄露内部芯片标识、开发机路径、会话证据 ID、过程产物或目标 API 的内部实现推理。公开安装路径、公开头文件和合法 API 标识保留实际技术含义；代码中的公开 intrinsic 或辅助函数不能仅凭名称删除。内部实现信息改写为有证据的用户可见行为，不混入 API 正文。

## 最终化

审阅通过后写入目标时间戳文件，并执行：

```text
node tools/ascendc-finalize.mjs <repo> --interface <documentApiName> --document <最终文档.md>
```

最终化脚本会再次检查冻结状态、未确认资料事实、逐项覆盖表、本次使用的 API、代码和资料是否变化、精确原型、调用示例和表格规则；校验失败时不得发布文件。只修复格式或与冻结事实一致的文案；若失败原因涉及新事实，返回补证或确认关口。

脚本的“审阅提示”表示编号或资源来源仍需判断，并非自动确认泄露。结合本次证据、数学含义和链接实际目标逐项核对，在交付说明中记录处理结论；不得只为消除提示改写技术含义。

生成或审阅前读取并遵守 `references/product-document-format.md`；其中定义产品名称、支持列表和差异化标签规范。
