# 代码证据编译

先按 `references/api-scope.md` 判断规则适用范围。Tensor/TPosition、寄存器、线程或队列等字段仅在当前成员实际涉及时核验；不适用项明确记录“不适用”，不要求构造对应对象。Tensor 参数需要时再读取 `references/tensor-parameters.md`。

## 目标与两种进入方式

建立本次 API 可追溯的 `code-evidence.md`。它不是只列出文件或先写一份概览，而是按本任务的必查范围，把能够支撑最终文档的代码事实、适用范围、证据位置和代码缺口逐项记录下来。

本任务有两种进入方式，使用同一套取证规则：

- **基础编译**：不读取可选参考资料；从已选 API 出发，完成本任务的全部必查范围。
- **资料触发回查**：`tasks/reconcile.md` 发现资料提出了 `code-evidence.md` 未记录的具体事实时，只针对该事实回读必要的目标代码链。资料只能告诉你“需要核验什么”，不能决定代码结论。

无论通过哪种方式，代码事实都必须追加写入 `code-evidence.md`。资料触发回查命中的事实要标明“提取方式：资料触发回查”，以便与基础编译区分；它不是另一份长期产物。

本阶段只产出代码事实、代码缺口和可定位证据，不写最终用户文档，也不读取可选参考资料来填补代码结论。

## 基础编译时不得读取参考文件

基础编译期间，主代理和任何子代理只能读取 `manifest.json` 与目标 API 的代码链。不得打开、全文搜索、摘录、引用或解析清单中任一状态为 `provided` 的资料；不得把这些文件或仓内 `docs/` 下的 Markdown 纳入代码搜索范围。若需要仓内搜索，应限制在代码和示例目录，或显式排除所有已提供资料及 `docs/`。

只有完成下列三项后，才能进入 `tasks/reconcile.md` 并完整读取已提供的参考文件：

1. 已按本任务的范围覆盖所有成员、重载、可达调用链和必查事实；
2. 已将可证实事实和代码缺口写入 `code-evidence.md`；
3. 主代理已复核代码证据的适用范围和文件定位。

参考文件中的词语、数值、约束或示例不得在基础编译中充当搜索关键词。资料触发的定向代码回查只会在 `tasks/reconcile.md` 完整读取资料后开始。

基础编译中的全文搜索必须使用 `tools/ascendc-code-search.mjs`；它自动排除 `docs/`、`outputs/`、测试目录、Markdown 与清单登记的参考文件。不得用无排除条件的仓内搜索替代它。

## 本次 API、代码范围与阅读顺序

进入本任务前，任务已提供 `manifest.json`。先完整读取它；不得创建、重写或根据任务文字补造其中信息。再读取其中的 `documentApiName`、`targetApi.members`、`apiType`、`callingConvention` 和 `files`，确定本次要写的 API、成员函数和代码范围：

- 每个 `member` 都是本次必须覆盖的公开成员；同名但未列在 `targetApi.members` 中、调用方式不同，或声明文件未列在 `targetApi.files` 中的 API，不能纳入原型、产品支持或行为证据。
- 逐个成员、逐个 overload 检查条件编译、产品支持、参数约束和调用链。常规接口与同步接口即使属于同一份文档，也不能假定行为相同。
- 关联公开接口只能提供语义或约束证据；其独有原型和形参不能并入当前文档成员。

资料收集前已生成本次 API 的临时调用关系定位结果；它只记录从已选成员出发可达的调用、`#include` 和宏表函数映射，不能作为代码事实或资料事实。执行下列代码阅读清单工具时必须复用该结果；输出均放入系统临时目录或直接读取标准输出，不得写入最终输出目录：

```text
node tools/ascendc-code-reading-plan.mjs --manifest <manifest.json> --relation-plan <temporary-api-relation-plan.json> --output <temporary-code-reading-plan.json>
```

代码阅读清单包含精确原型、跨目录 `#include` 和实现闭包、公共包装接口的参数传播候选、调用示例位置，以及受限搜索边界。它只是阅读计划，不是最终事实。

其中 `semanticLinks.scannedFileCount` 仅表示自动建立调用关系索引时读取过多少源码文件，不表示这些文件已经被理解、核验或形成事实。`referenceClosure` 是完整 `#include`、宏、类型和未解析引用的定位索引，只在需要定位时查看，不进入逐项人工核验。`codeClosure.candidateFiles` 才是本次目标 API 的初始直接证据闭包；进入代码证据阶段后，必须逐项记录处理结果。`apiRelations` 中的直接调用和原始宏表映射只用于定位待核验代码或资料；宏映射须结合 `macroMappingGroups` 的实现族、条件和实际类型组合审阅，不能把表中可能条目当作当前 API 已使用的行为。每项都保留当前成员、条件、调用位置和定位结果，不能直接写入最终文档。`publicContracts.contracts` 是从目标成员公开声明紧邻注释中提取出的待核验候选，保留原文件和行号；它们不是自动成立的文档结论。

`semanticLinks.callCandidateDiagnostics` 记录了同名调用候选的筛选过程：工具会结合调用所在的芯片条件、调用方式、参数类别和参数个数排除不匹配的实现。`resolved` 表示只剩一个可达实现；`resolved_overload_family` 表示同一文件、同一调用方式、同一芯片条件且参数类别一致的一组真实重载都可能成立，必须按适用数据类型分别核验，不能把它写成唯一重载的结论。`ambiguous`、`no_compatible_candidate` 和 `unresolved_scoped_member` 表示工具已停止自动向下追踪；最后一种是类型别名、对象或指针成员调用，不能因成员名相同连接到裸函数实现。其中列出的实现都不能作为当前 API 的代码事实，只有为解决某个具体事实回读当前直接代码链后才能另行判断。

## 受控源码阅读、分工与主代理合并

主代理先完整读取 `manifest.json`，执行一次代码阅读清单工具；在打开任何目标源码文件前，依据清单中的精确原型、调用关系、语义链和 `searchBoundary`，按“成员/overload × 核验项”列出本次必查范围及分工。核验项例如完整原型、参数单位、同步行为、产品条件或输出状态。

基础编译中的全文搜索一律使用下列受限工具；它只搜索代码仓中允许的代码或示例路径，自动排除 `docs/`、`outputs/`、测试目录、Markdown 和清单登记的参考文件：

```text
node tools/ascendc-code-search.mjs --manifest <manifest.json> --pattern <精确符号> --path <阅读清单或直接调用链给出的仓内代码路径>
```

不得要求或执行“搜索整个仓库”；读取清单列出的文件，也不等于可以搜索其余 Markdown、资料或文档目录。直接打开的源码必须来自阅读清单，或由已读代码中的直接调用、`#include`、条件分支明确引入。

在开始取证前，将 `codeClosure.candidateFiles` 的每项写入 `code-evidence.md` 的“源码处理记录”。每项只能以以下终态收口：`已核验并形成事实`、`已核验，无当前 API 事实`、`不适用`。后两种也必须写明实际核验范围和结论理由；读取失败、待补读或只知道文件路径都不是终态，不能完成代码证据。只有已读代码实际证明某个额外文件是当前 API 的直接类型、约束、调用、宏或实现链的一环时，才能追加为“新增直接证据链文件”；逐个列出文件、触发位置和原因。不得把定向搜索未命中、完整 include 索引或示例工程支撑文件写入“源码处理记录”。自动索引文件数不能代替这张记录，也不要求逐一人工阅读自动索引到但未进入候选代码闭包的全部文件。

对每条 `semanticLinks.callCandidateDiagnostics`，在“调用候选核验”中记录调用位置、保留或停止的结果、每个被排除或无法确定候选的文件和行号，以及具体理由。被自动排除的同名实现不因名称相同而加入“源码处理记录”，也不得作为事实来源；`ambiguous` 或 `no_compatible_candidate` 不能任选其一继续追踪，应写入代码缺口或只在解决具体事实时沿当前成员的直接调用链人工核验。

对 `publicContracts.contracts` 的每条公开注释候选，打开原始声明核对成员、overload 和条件分支后，在“公开注释核验”中记录相同的终态。只有确属当前成员、适用范围一致的注释才能形成 K-ID；内部实现注释、脱离声明的注释或条件不一致的注释必须记录为“无当前 API 事实”或“不适用”，不得直接写入文档。

代码阅读清单显示两个及以上可以独立核验的范围时，运行环境具备子代理工具就必须交给子代理阅读；先为每个文件或可分离片段指定唯一的深读责任方，不得把同一完整文件交给多个子代理。共享文件只能按互不重叠的符号或行段分工，并在返回中写明边界。

| 阅读职责 | 重点查证的代码与事实 |
|---|---|
| 公开接口与示例 | 完整原型、公开注释、模板参数、公共结构体/枚举、条件编译，以及与当前成员实际匹配的调用示例。 |
| 功能与参数语义 | 可达 wrapper、`Impl`、`Cal`、最终计算或分发函数；参数传播、隐含语义操作数和可确认公式。 |
| 校验、组合与状态 | `api_check`、`kernel_check`、tiling、host 校验；dtype/TPosition、地址复用/对齐、临时空间、输出初始化和状态影响。 |
| 产品支持与差异 | 当前成员可达链上的 `AddConfig`、架构条件、支持/不支持路径，以及用户可见的产品差异。 |

运行环境支持并发派发时，必须在查看任一子代理结果前同批发出全部范围不重叠的任务，再等待结果；若工具调用会逐项返回，则如实记录为“子代理分工（串行返回）”，不得称为并行。一次任务失败后，只重派尚未完成的最小范围，不得以原始完整范围重复派发。运行环境没有子代理工具、代码闭包极小或职责彼此不可拆分时，主代理可以直接阅读，但必须在 code-evidence.md 中写明原因，且仍须完成相同的覆盖检查。

每项子代理任务都必须提供以下只读输入：

- 同一份 `manifest.json`；
- 明确的成员、overload 和核验项范围；
- 代码阅读清单给出的初始文件、符号和 `searchBoundary`；
- 本任务中与该范围相关的取证规则。

子代理只能阅读已分配范围及其明确可达的直接调用链；全文搜索必须使用上述受限工具。不得读取可选参考资料、编写最终用户文档、创建或修改 `code-evidence.md`，也不得分配 `K-ID`。

子代理只返回取证结论条目。每条至少包含：

```md
### <事实标题>
- 核验项：...
- 候选结论：...
- 适用范围：成员 / overload / 产品 / 条件。
- 代码证据：`relative/file.h:123`，符号或分支；必要时附最小摘录。
- 已查范围：文件、符号、分支和进入原因。
- 证据状态：已证实 / 缺口 / 需开发确认。
- 未证实原因或冲突说明：...
```

子代理发现直接调用、`#include` 或条件分支需要继续追踪时，可以依照本任务的代码闭包规则补读；返回时必须说明新增文件、进入原因以及它与目标成员的可达关系。不得因相近名称、目录、后缀、同族关系或另一 API 对同一 intrinsic 的调用扩大范围。后一种调用至多是间接线索，不能单独证明当前 API 的参数单位、合法范围、逐值行为或数据类型组合。

每个核验项指定一个主要负责方。主代理先核对返回结论的成员、条件、定位和适用范围；只有发生结论冲突、缺少定位、范围无法判断或发现新的直接可达分支时，才回读对应的最小代码片段。不得把常规复核变成已由子代理完整核验文件的全文重读。不同子代理可以为同一核验项提供上下文，但不能各自把它写成独立的最终结论；结论不一致时先回读源码，不以多数意见决定。只有主代理能写入 `code-evidence.md`、分配稳定 K-ID，并登记代码缺口。

合并后，主代理按“成员/overload × 必查事实范围”检查覆盖度。缺少的核验项必须形成更小范围的定向源码阅读任务；不能因为已有子代理结果就宣告代码证据完成。资料触发回查也要先作同样的分工判断，在“代码阅读分工”中新增回查批次及其返回的 `K-ID`；范围只能是待核验的具体事实及其直接代码链，最终写入时标明“提取方式：资料触发回查”。

按以下顺序建立并阅读目标 API 的代码闭包；无论由主代理还是子代理阅读，每个进入的文件都要返回进入原因；主代理合并后在 `code-evidence.md` 中记录：

1. 所选成员的公开声明/定义、Doxygen 注释、模板和条件编译；
2. 直接 `#include` 的公共头、`*_utils.h`、`*_common.h`、结构体和枚举定义；
3. 当前成员可达的 wrapper、`Impl`、`Cal`、最终计算或分发函数；
4. 当前成员可达的 `api_check`、`kernel_check`、tiling 和 host 校验；
5. 当前成员直接调用的基础 API；若调用链进入 `impl/basic_api/dav_*/kernel_operator_*_impl.h` 或 `impl/basic_api/kernel_operator_*_base_impl.h`，必须阅读相应可达实现。阅读清单未列出但调用链明确进入时，先补入闭包，再取证；
6. 与当前成员实际调用相符的 `examples/` 示例。

在需要解释某个事实时，允许从上述文件继续跟到直接被调用的头或实现；不得因为同目录、相近名称、相同后缀、同族接口或类似功能而扩大到无关 API。仓内 Markdown、测试目录和与目标成员无直接关系的辅助代码不能作为代码事实来源。架构背景资料只能帮助理解术语，不能替代 API 行为或产品支持证据。

## 必查事实范围

基础编译必须按下列范围逐项检查，而非只记录最先注意到的信息。每项都要按成员、overload、产品和适用条件拆分；没有可读证据时写入代码缺口并说明已查范围。

1. 完整函数原型、模板参数、调用约定、返回类型和成员覆盖；
2. 固定产品项的支持/不支持以及产品差异；
3. 公开功能、真实使用场景、可确认公式和公式变量含义；
4. 每个模板参数、形式参数、结构体字段和枚举的方向、语义、类型、默认值、单位、范围、可取值和适用条件；
5. 数据类型、TPosition、产品限制和多参数组合；
6. 单参数约束、地址复用/对齐、临时空间、状态影响和输出初始化需求；
7. 真实调用示例的位置、调用前提和可确认的结果关系。

## 1. 原型、成员与公开边界

- `## 函数原型` 必须逐字保存代码阅读清单提取并经源码核对的完整签名，覆盖每个成员和 overload；模板行、调用约定、形参名、顺序、限定符、返回类型与分号不得改写。
- 头文件中同名的不同调用方式、非成员后缀接口或未选成员不能因名称相近而合并。参数名序列只用于精确关联证据，不能被写成用户可见的功能分类。
- 公开注释、公开 wrapper、公开结构体字段和可达检查可用于建立用户语义。底层 intrinsic、helper、`Impl`/`Cal`、寄存器设置和内部文件路径只可作为证据定位，不能被包装成用户功能、公式、模式或场景名称。
- `__inout_pipe__(...)`、`#pragma begin_pipe(...)` 等编译限定符或管线标记只可按代码原文记录；除非源码明确把它规定为用户可见约束，否则不得自行翻译成执行管线术语。

## 2. 产品支持与芯片差异

只接受当前 API **有效代码链路**上的显式证据。有效代码链路是：目标成员的声明、函数体、可达 wrapper/`Impl`/`Cal`、参数校验、最终计算或 intrinsic 分发、tiling/host 校验。通过 `#include` 引入的文件中，只有能由目标成员到达的分支才有效；同文件的其它 API、其它 overload、未调用 helper 或不可达分支不能作为当前 API 证据。

对代码闭包中的每个成员查找并核验下列候选：

- `AddConfig("芯片名", ...)`；
- `SocVersion::...`、`NpuArch::...`、`GetCurrentPlatformInfo().GetCurNpuArch()` 条件；
- `#if`/`#ifdef` 中的 `__NPU_ARCH__`、`__CCE_AICORE__`、DAV 宏；
- 当前可达的 `IsRegBase(...)` 或 `isRegbase(...)`；
- 分支内的 dtype、参数校验、tiling、临时空间、实现分发和功能行为差异。

候选命中后必须验证其从目标成员可达，并继续检查是否进入 `ASCENDC_REPORT_NOT_SUPPORT`、`NOT_SUPPORT`、恒 false 断言、`static_assert(false)`、空实现或纯报错路径；这些路径不能证明支持。禁止由共用实现、相似分支、产品系列归属、文件中出现芯片名或模型常识推断支持。

按 `references/chip_mapping.md` 将有效代码标识映射为以下固定对外产品项，顺序不可变：

1. Ascend 950PR&950DT系列产品
2. Atlas A3系列产品
3. Atlas A2系列产品
4. Atlas 200I/500 A2推理产品
5. Atlas推理系列产品AI Core
6. Atlas推理系列产品Vector Core
7. Atlas训练系列产品

每一项都记录“支持”或“不支持”、成员/overload 适用范围和可达代码证据。没有有效显式证据时结论为“不支持”，不能写成“可能支持”。代码内部芯片标识可保留在证据定位中，不能作为面向用户的产品名称。

产品差异必须分别记录 dtype、原型可用性、参数约束、计算路径和功能特性中的实际差异。内部实现函数不同本身只说明代码路径不同；只有能从公开语义或明确检查得出的用户可见差异才可形成语义事实。

## 3. 功能、公式和参数语义

按事实类型采用最直接的来源：公开接口头和 Doxygen 注释用于基础语义、方向、模板默认值与显式约束；公共头用于结构体/枚举；tiling 与 host 代码用于数值范围、合法组合和警告；kernel check 用于硬约束；实现仅用于补证行为是否真实影响结果。来源不完整时，不能用低层符号或名称猜测补齐。

### 功能和公式

- 功能、使用效果和场景必须来自公开注释、公开 wrapper 或可确认的公开参数行为。函数重载或参数中出现 `count`、`repeat`、`stride`、`sync` 等，不足以自行创造功能模式名称。
- 只有公开代码明确给出数学/映射关系时才记录公式。搬运、配置、同步、包装、寄存器状态设置或格式转换接口可以没有公式。
- 公式中的每个形参、模板参数、结构体字段、临时变量、下标、集合、范围和单位换算量都要有解释；下标必须给出取值范围。控制地址、范围、步长、重复、mask、axis、shape、block/gap/stride 的参数要么在公式或变量说明中明确，要么不输出公式并记录缺口。
- 不能把 `intrinsic(dst, src, ...)`、helper 调用或内部实现函数名改写成用户可见公式。若只看见参数转发，记录“内部实现证据不足以形成用户语义”。

### 参数、结构体和枚举

每个模板参数和形式参数都要检查方向、类型与语义；默认值、单位、范围、数据类型、TPosition、产品条件、配置方法、特殊值及参数关系仅在当前参数适用时核验。对结构体，记录字段类型、默认值、可确认范围、字段含义和用户是否需要配置；对枚举，区分“完整枚举定义”和“当前接口支持取值”，不能互相替代。

- C/C++ 整数类型只证明存储类型和可表示范围，不能证明接口合法范围。没有注释、校验、实现分支或明确指令证据时，范围是代码缺口。
- `\note support data type:`、模板特化、`enable_if`、`SupportType<Tuple<...>>`、显式断言和产品条件只能在目标成员的有效链路上使用；同文件其它接口的 dtype 不能混用。
- 对 `mode`、`pattern`、`flag`、`enable`、`source`、`repeat`、`stride`、`gap`、`len`、`burst`、`count` 等控制参数，建立“目标形参 → 下游实参位置/结构体字段 → 检查或分支 → 最终行为”的证据链。只有名称、下游变量名、同族 API 名或数值后缀时，仍只是线索。
- 参数只转发到内部符号时，必须按完整符号名和同一实参位置进行精确语义旁路追踪：回读关联公开 API、公开 wrapper、公开结构体、check 或明确指令映射，形成闭环后才可确认语义。关联公开接口不是当前文档成员。
- 旁路追踪只证明实参映射时，不能据此断言单位、合法范围、逐值行为或数据类型组合。测试中哨兵值的透传也只能证明透传，不能证明该值合法。
- 当下游结构体字段揭示没有显式形参的语义操作数时，将其作为“隐含语义操作数”记录，绑定控制它的正式参数、适用条件和证据；不能伪造新的参数表行。
- 对 `reserved`、`unused`、`internal`、填充字段或默认初始化字段，不得只凭名称和默认值判定为无需配置。沿 wrapper、实现、check、地址/shape/临时空间/类型组合与最终计算追踪：未被消费且无用户配置证据时才可判定为保留或内部字段；参与任一行为、校验或分支时不能作此判定。不同产品、overload 或路径结论不同则拆分记录。

## 4. 约束、组合与状态

对约束按最直接的来源交叉核验：kernel check 的显式检查优先用于硬约束；tiling/host 的范围、组合、warning 和临时空间计算随后使用；公开注释与条件编译补充；实现用于确认约束是否实际影响行为。必须明确约束属于哪个成员、overload、产品和参数集合。

- 地址复用/重叠约束从目标成员可达的 `TensorReuseVerifyingParameters`、参数元组和实际检查中取得；未出现在检查参数集合中的形参不能被推断为受该约束。
- 地址对齐只能来自当前 API 的注释、显式 check、tiling 校验、显式对齐计算、调用示例或已建立映射的明确指令要求。TPosition 和物理存储位置不能单独证明地址对齐；没找到校验也不等于没有要求。
- tiling 文件中的独立辅助 API（例如独立的临时空间查询接口）有自己的参数检查时，不能把该检查归入目标 API；只有目标 API 实际需要调用该辅助接口的关系可作为使用提示。
- 多参数共同决定 dtype、TPosition、shape、范围、地址、数据排布或功能时，必须记录为多参数组合约束。按真实原型、产品和代码路径保留全部参与参数及每个明确组合，不能压缩成单参数集合、并集或“同上”。
- 不同产品、overload、结构体或分支的组合不一致时分别记录；路径未覆盖是代码缺口，代码证据相互矛盾或需要接口 owner 裁定时标为 `【需开发确认】`。
- 对输出参数额外检查实现是否覆盖写入、读取原值累加或原地更新。只有覆盖写入且未读取原值才能记录“不需要调用前清零”；读取原值参与累加、归约、原地更新或明确要求清零时记录“需要初始化/清零”；无法证明时记录代码缺口，不能在示例中自行加入清零。
- 检查调用是否改变会影响后续用户代码的全局状态，例如 mask 或向量寄存器。只有用户需要显式配合或恢复时才形成用户约束；接口内部成对 helper 只作为内部证据。

### 对外事实候选

公开原型、`static_assert`、默认值、参数或字段的 mask 传播、返回值传播和 wrapper 新增限制，若已由当前成员的可达代码证实，必须逐条作为候选记录。候选必须写清成员/overload/产品/条件、源层以及是否为逐参数原样透传。下层 API 的约束只有在当前 overload 明确原样透传相应参数、方向、条件与返回行为时才能成为候选；无法证明时写入代码缺口或后续用户确认，不得借用下层文档扩展当前 API 的承诺。

测试覆盖、构建、编译、运行、golden 或工程验证状态不是 API 对用户的约束，不能写入候选或最终 API 文档，只能保留在证据或测试产物中。

## 5. 调用示例

调用示例首先只从代码仓 `examples/` 中取得。读取代码阅读清单的 `callExample`：对每个成员，确定性提取只接受包含当前成员直接调用的 `Compute()`；没有这种 `Compute()` 时才接受包含当前成员直接调用的 `Process()`。文件名、目录名或整个文件出现 API 名称都不足以成立，必须核验所选函数体中的真实调用，并记录文件路径、函数名、行号、前置配置和可确认结果关系。

仅当某成员未找到上述结果、但返回了 `helperCandidates` 时，阅读 `tasks/example-call-chain.md`，由模型在候选指定的同一 `.asc` 文件内受限核验 Helper 调用链；不得重新扫描整个 `examples/`，不得读取资料，也不得把模型推测作为代码事实。模型核验出调用链或 Helper 片段后，应将其作为代码仓示例结果记录；只有确定性提取和该回退都没有可用结果时，才记录仓内示例缺失并在资料阶段按 `tasks/reconcile.md` 回退。示例只证明其中实际出现的用法，不能扩大为全部合法范围或产品支持。
