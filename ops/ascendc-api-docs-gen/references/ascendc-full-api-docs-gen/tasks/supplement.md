# 确认后的覆盖检查与定向补证

先按 `references/api-scope.md` 判断规则适用范围。Tensor/TPosition、寄存器、线程或队列等字段仅在当前成员实际涉及时核验；不适用项明确记录“不适用”，不要求构造对应对象。Tensor 参数需要时再读取 `references/tensor-parameters.md`。

## 目标与边界

用户完成首轮确认后，检查每一条准备写入文档的具体知识是否已经有足够依据；只补读缺失或受影响的目标代码链，不重新开展宽泛搜索。

资料中出现、但首轮代码证据没有记录的具体事实，必须已经在 `tasks/reconcile.md` 的“资料触发的代码回查”中处理。每个 G-项都必须已有 K-项、C-项或 S-项结果；没有明确结果时返回对齐阶段，不能在这里跳过。S-项表示“代码回查后仍未证实、但可能保留的资料事实”，不是实际冲突。`other-api`、`peer-api` 或 `excluded` 资料不产生 R/G/C/S 项，也不能写入覆盖表；`peer-api` 只能在“调用示例组成依据”中作为结构模板。`downstream-api` 的 D-ID 只有在“下层资料适用性”表逐条决定为可写入后，才可作为覆盖表依据；`mixed-api` 资料只能使用明确属于当前 API 的 R-ID。

本阶段只处理：

- 回查、用户确认后仍未覆盖的文档必需项；
- 已确认事实需要进一步限定的成员、条件、组合或用户可见语义；
- 新补证影响已确认事实时的二次确认。

不得把资料直接当作代码结论，不得扩展到无关 API，也不得静默推翻用户决定。

## 覆盖与待补证表

先从完整函数原型、已确认事实和最终文档章节，列出本次实际需要的具体知识项。每一项都按成员、overload、产品和条件拆开；“槽位”是待写入文档的一条具体知识，例如“`_sync` 在 AIV 路径上的状态影响”，而不是一个笼统章节。

必须在 `resolution.md` 写入真正的 Markdown 表格，不能只写“已全部覆盖”：

```md
## 覆盖与待补证
| 槽位 | 适用范围 | 状态 | 依据 |
|---|---|---|---|
| <具体知识项> | <成员 / overload / 产品 / 条件> | <状态> | K-001 / C-001 / S-001；必要时说明缺口 |
```

至少检查下列适用于本次 API 的项：

- 每个成员、overload 的原型和调用约定；
- 固定七项产品支持，以及有证据的 dtype、原型、参数、计算路径和功能差异；
- 功能、可确认公式和公式变量闭包；
- 每个模板参数、形式参数、结构体字段、枚举完整定义与当前支持取值、隐含语义操作数；
- 返回值、输出初始化、单参数约束、跨参数组合、地址复用/对齐、状态影响和产品限制；
- 可验证或可构造的调用示例及结果关系。

每行只能使用下列状态之一：

- `已由代码证实`：有适用范围一致的 K-ID。
- `经用户确认并允许保留`：用户通过 `question` 选择保留的 C-ID 或 S-ID，且决议记录完整。
- `用户明确暂缓`：用户明确选择暂缓，最终文档须显示 `【待开发补齐】`。
- `不适用`：已有 K-ID 证明该字段不属于当前成员或参数，并在依据列写出具体原因。K-ID 必须存在于 code-evidence.md；不能用未发现代码、未知或只有 K-ID 而无原因来代替不适用。真正的尚未确认仍需补证或明确暂缓。
- `待代码补证`、`待确认`、`需二次确认`：非终态，不能冻结。

不要另建 `coverage/matrix.json`；覆盖表与其依据始终保存在 `resolution.md`。

## 示例使用限制

冻结前必须维护 `resolution.md` 中的“示例使用限制”表和“调用示例组成依据”表。后者先写“示例来源”行，再逐项列出核心调用、参数、输入数据、结果说明以及（如使用）工程/Host/Kernel/CMake 结构的依据。来源只能依次为：代码仓 `examples/` 中经核验的 `Compute()` / `Process()`、按 `tasks/example-call-chain.md` 核验的 Helper 调用链或 Helper 片段、同 API 资料中的经核验示例、当前 API 实现与同类 API 的结构模板；只有前一项不存在或不可用才可进入后一项。`peer-api` 资料只能出现在工程结构类行，不能为目标 API 的参数、输入、结果或行为背书；`downstream-api` 资料不能作为当前 API 的调用示例来源；每一项目标 API 内容仍须指向当前 API 的 K-ID、R-ID 或已确认事实。每个会影响调用示例的未证实行为都要有一行，分别列出成员、受限制对象、已证实的允许范围、不得使用的触发条件、可静态拦截的写法和依据。

- `示例只能使用`必须是可执行的允许范围，不能是“正常”“适当”“待确认”或“待补齐”。
- `校验写法`有可直接识别的代码字面量或表达式时，逐项使用反引号列出；无法静态匹配时写“人工审阅”。
- 本次不存在会影响示例的未证实行为时，仍保留一行“全部成员 / 无 / 按已确认原型和事实 / 无 / 无 / 本次未发现会影响调用示例的未证实行为”。
- 某个未证实行为会影响示例、但没有已证实的允许范围时，该槽位仍需补证，不能以“用户明确暂缓”冻结后再用任意示例输入绕过。

## 定向补证方法

从缺失项所属的目标成员、原型和已确认的直接代码链出发，完整遵守 `tasks/evidence.md` 的阅读范围、来源优先级、受限搜索和不可推断规则：

1. 先核对公开声明、注释、参数/模板、结构体和枚举；
2. 再读取直接 wrapper、实现、`api_check`/`kernel_check`、tiling、host 校验和最终调用；
3. 对控制参数、隐含语义操作数和内部调用，按完整符号与同一实参位置做精确旁路追踪；
4. 对产品、组合、对齐、输出初始化和状态影响，回读该项实际适用的条件与分支；
5. 需要全文定位时使用 `tools/ascendc-code-search.mjs`；需要新增文件时先更新临时代码阅读清单，并在 `code-evidence.md` 的“代码阅读分工”记录本批范围、阅读方式、执行者和返回的 K-ID。

另一 API 对同一 intrinsic 的调用只能给出间接线索，不能单独补足当前 API 的单位、范围、逐值行为或数据类型组合。补证得到的代码事实追加到 `code-evidence.md`，并在 `resolution.md` 的覆盖表和决策变更记录中标明新增 K-ID、受影响的 C-ID/S-ID/G-ID。

- 代码证实已确认事实：将对应覆盖行改为“已由代码证实”。
- 代码补充了事实但不改变已确认范围：保留最终值并更新依据。
- 代码仍没有给出答案：保留用户已确认的资料事实，或按用户的“暂缓”写 `【待开发补齐】`。
- 代码与确认事实不兼容、扩大/缩小适用范围或揭示不同组合：将对应行改为“需二次确认”，追加候选和变更记录，再回到 `tasks/reconcile.md` 的 `question` 流程。

## 冻结条件

只有本阶段才能把 `resolution.md` 冻结。冻结前必须同时满足：

1. “覆盖与待补证”表存在，并且每条本次必需项都有一行；
2. 表中每一行均为“已由代码证实”“经用户确认并允许保留”“用户明确暂缓”或有代码依据及具体原因的“不适用”；
3. `unresolvedConflicts: 0`；
4. `pendingReferenceApprovals: 0`；
5. 不存在待确认、需二次确认或没有结论的 G-项；
6. 每份 `provided` 资料的 `documentTarget` 均为终态：`current-api`、`mixed-api`、`peer-api`、`downstream-api`、`other-api` 或 `excluded`。
7. “下层资料适用性”表存在；每个 D-ID 都已有终态处理，且任何“写入当前 API 文档”或“经用户确认写入当前 API 文档”的行都记录了 K-ID、C-ID 或 S-ID。
8. “示例使用限制”表和“调用示例组成依据”表均存在；每个影响调用示例的未证实行为均已写入具体允许范围和依据，且同类 API 资料仅被作为结构模板使用。
9. “对外事实映射”表存在，且与 `code-evidence.md` 的“对外事实候选”逐条一一对应；所有写入正文的事实保留候选的适用范围、来源与透传关系、正文位置和必含标识符。

满足后才把 front matter 改为：

```md
status: frozen
unresolvedConflicts: 0
pendingReferenceApprovals: 0
```

任一条件不满足时保留非冻结状态并停止生成。覆盖表和决议始终保存在 `resolution.md`，供最终化工具检查。
