# AscendC API 文档生成

## 目录导航

- `tools/`：创建清单、确认接口、资料登记和最终化入口。
- `scripts/`：接口解析、代码关系与确定性校验。
- `tasks/`：各关口的详细执行规则，进入对应关口时读取。
- `references/`：产品、术语和跨目录取证参考，按需读取。

## 运行依赖

Markdown 检查首次实际解析时从固定版本 CDN 下载解析器与上游许可证，按 [依赖清单](scripts/lib/markdown-it-dependency.json) 校验 SHA-256 后加载；不使用 latest。两模块默认共享用户目录下 `.cache/canndoc-api-docs-gen` 缓存，也可用 `CANNDOC_DEPENDENCY_CACHE` 指定可写缓存根目录。有效缓存可离线使用，损坏或缺失时重新下载；网络、写入或校验失败则停止，不跳过文档检查。仅导入工具模块不会下载。

离线环境使用前，可联网执行 `node scripts/lib/markdown-it-loader.js --prepare`，再将包含解析器和许可证的缓存提供给离线环境，并设置缓存根目录；也可用此命令提前准备当前用户缓存。首次无缓存运行需要访问清单中的 HTTPS 地址。

## API 范围与按需规则

先读取 [API 范围与规则路由](references/api-scope.md)，将接口类别与调用约定分别登记。仅在原型或关联类型实际涉及 Tensor/TPosition 时加载 Tensor 参数参考；其余接口不要求 Tensor 对象、队列或 Compute/Process 入口。术语使用对应版本的公开官方资料，不能依据词表机械改写代码或技术含义。

## 使用入口与资料收集

先区分本次任务尚未提供清单，还是已有清单不存在或不可读。用户已说明清单不可用时，报告当前阻塞并请求可读路径即可，不搜索其它清单、接口或代码仓来替代。

- **已有 `manifest.json`**：完整读取该文件。它登记已选 API、代码仓、成员函数、调用方式和资料记录；不得创建、重写其中的 API 信息，也不得根据任务文字重新拼装 API 信息。后续查阅的代码和资料都以它为准。
- **未提供 `manifest.json`**：完整读取 `tasks/create-manifest.md`，按其输入收集和交接规则处理；信息齐全后通过该任务指定的唯一入口创建标准 v2 `manifest.json`。成功后完整读取新清单，再进入本节的资料收集步骤。
- **明确给出但不可读的 `manifest.json` 路径**：停止并报告路径问题；不得改为创建新的 `manifest.json`，避免覆盖或分叉已有记录。

`manifest.json` 的资料列表中默认有“内部脱敏资料”和“仓内已有人工文档”两项，也可以有任意名称的额外资料；每一项只对应一个文件。

## 确认最终文档接口

在询问资料、运行调用关系分析或读取目标代码前，完整读取 `tasks/confirm-final-api.md`。清单中的 `finalApiConfirmation` 为 `confirmed` 时不再询问；为 `pending` 时必须用 `question` 展示接口名称、类别、调用方式、覆盖成员和接口文件，让用户确认本次最终要写的接口。

用户确认后使用 `tools/ascendc-confirm-target-api.mjs` 持久记录，并重新读取 `manifest.json`。用户否认时停止当前任务，不能在原清单中替换 API。下层 API、同类 API 和它们的文档都只是后续可确认用途的资料，不能替代最终接口。

在确认最终接口后、询问或读取任何资料文件前，先用已选 API 生成临时调用关系定位结果：

```text
node tools/ascendc-api-relation-plan.mjs --manifest <manifest.json> --output <temporary-api-relation-plan.json>
```

它只记录当前成员可达的 `#include`、调用和宏表函数映射，用来寻找可能相关的仓内文档；它不是代码事实，不能写入最终文档，也不能读取资料内容。后续运行仓内文档查找和代码阅读清单时都复用同一临时结果。

逐项处理资料状态：

- `provided`：路径可读且已登记，跳过询问。相对路径已按清单中的代码仓根目录解析；记录中同时保留用户输入和解析后的绝对路径。
- `pending`：除“仓内已有人工文档”外，立即用 `question` 询问该资料名称是否有文件；有则请用户在 `Other / 自行输入` 填写路径，没有则选择“没有此资料”。内部脱敏资料只能由用户提供路径，不能在代码仓中自动寻找。
- `unreadable`：说明此前尝试的完整路径和不可读原因；让用户提供替代路径或确认“没有此资料”。
- `absent`：用户已明确确认不存在，不再询问。

“仓内已有人工文档”仍为 `pending` 时，运行：

```text
node tools/ascendc-find-existing-document.mjs --manifest <manifest.json> --relation-plan <temporary-api-relation-plan.json>
```

结果按四组返回，候选始终只是待用户确认的路径，不能直接当作资料事实：`currentApiCandidates` 仅保留与当前 API 同类别、且以文件名、一级标题、明确章节或“函数原型”章节中的声明精确锚定的文档；`peerApiCandidates` 是同一 API 类别的其它接口文档，只可作调用示例工程结构模板，至多三条；`downstreamApiCandidates` 仅包含已直接解析到的下层 API 文档；`macroMappingGroupCandidates` 将宏表映射按同一实现模板归组，完整逐行映射和条件仍在临时调用关系结果中，候选结果只提供供筛选的摘要和文档元数据。

对每个宏映射组，先阅读临时关系结果指定的当前 API 声明、直接实现、宏定义和宏表位置，再由模型结合组的条件、类型组合和调用路径，从该组候选中推荐零到三份真正可能有用的下层文档。模型只能使用已有组、关系 ID 和代码位置作出推荐，不能把宏表中的可能映射说成已使用的行为，不能自行补造下层关系或技术事实；当前 API 未固定到具体下层 API、类型组合或产品条件时，推荐“无需下层文档”。候选文档正文在用户确认前不得打开。

按以下规则使用 `question` 确认候选：

1. 当前 API 候选可按需选择；同类 API 至多选择一份，仅作示例工程结构参考。
2. 每个直接下层候选及上一段推荐的宏映射组候选，分别确认使用或拒绝。问题展示完整路径、匹配 API、关系/组、条件和代码定位；关系存在不代表同意使用。
3. 保留 Other / 自行输入 路径入口。自行提供的路径先保持未判定，由 `tasks/reconcile.md` 完整阅读后确定适用性。
4. 第一份选中资料登记为“仓内已有人工文档”，其余按清楚的资料名称新增。确认候选后写入 current-api、peer-api 或 downstream-api 关系，记录检测 API 和候选原因。
5. 无候选或全部被拒绝时，询问是否提供其他路径或确认不存在；只有用户明确确认不存在，才能登记为 absent。

用户给出路径后，使用 `tools/ascendc-record-reference.mjs` 按该资料的 `id` 登记；路径不可读时工具会保留“不可读”状态和原因，不得把它误记为不存在。用户确认不存在时也用该工具持久登记。每次登记后重新读取 `manifest.json`，不得改写已选 API、成员函数、调用方式或代码入口。

当 `manifest.json` 的“其他资料已收集完毕”尚未确认时，再用一次 `question` 询问：`本次是否还有其他可供参考的资料？如有，请用“资料名称：文件路径”的形式列出，可一次提供多条；如没有，选择“没有其他资料”。` 对每条新增资料分别登记；用户确认没有后，登记资料收集完成。只有全部资料为 `provided` 或 `absent`，且已完成这次“其他资料”询问，才能读取 `tasks/evidence.md` 并进入代码证据阶段。

若 `manifest.json`、已登记代码或状态为 `provided` 的资料无法读取，停止并报告错误；绝不把路径为空、读取失败或 `pending` 概括为“没有资料”。

## 长期产物

默认输出目录为 `<代码仓>/outputs/<API名称>/`。符号运算符 API 使用可读的语义产物名，例如 `operator+` 的目录和最终文档文件名前缀均为 `operator_add`，`operator|` 对应 `operator_bitwise_or`；`manifest.json` 中仍保留源码的原始 API 名称，并以 `output.documentFileStem` 记录文件名前缀。已有百分号编码目录可以继续读取，不自动改名。长期只保留：

```text
manifest.json
code-evidence.md
reference-evidence.md
resolution.md
<API名称>_YYYYMMDDHHmm.md
```

- `manifest.json` 记录本次使用的 API、代码和资料状态；来源发生变化时，用它判断哪些确认结论需要重新核对。
- 三份 Markdown 分别保存代码事实、每份已提供资料的事实、用户决议与覆盖状态；它们是模型和人工审阅的主要上下文。
- 临时调用关系定位结果、临时代码阅读清单、临时草稿和工具日志只能位于临时目录；不得复制资料全文到长期产物。

## 工作流

严格按下列关口推进。每个关口开始前完整读取对应 task 文件。

| 关口 | 必读任务 | 主要输入 | 长期输出 | 放行条件 |
|---|---|---|---|---|
| 代码证据编译 | `tasks/evidence.md` | `manifest.json`、代码仓 | `code-evidence.md` | 覆盖所有已选成员、完成代码调用链、必查事实和代码缺口记录 |
| 事实对齐、资料触发回查与确认 | `tasks/reconcile.md` | 代码证据、全部已提供资料 | `reference-evidence.md`、`resolution.md` | 新出现的资料事实已完成定向代码回查；每个实际冲突和需保留的未证实资料事实均已裁定或暂缓 |
| 定向补证 | `tasks/supplement.md` | 已确认事实、代码证据 | 更新证据与决议 | 所有必需事实已覆盖、暂缓或再次确认 |
| 生成与审阅 | `tasks/generate.md`、`tasks/review.md` | 三份长期产物 | 最终 Markdown | `resolution.md` 已冻结且校验通过 |

### 代码证据方法

代码阅读清单工具在取证前把候选代码闭包的文件摘要登记到 `manifest.json` 的 `sources.repo.evidenceFiles`，并更新来源指纹；执行后重新读取清单再编写证据。新增直接证据文件先用同一工具的 `--source-file <路径>` 登记（可重复，相对于代码仓），然后读取并核验。旧文件已变化时工具停止，不用当前摘要覆盖旧摘要；按既有归档、新会话和补证规则处理受影响事实。旧会话缺少快照时返回取证阶段，不在最终化时补记摘要并沿用旧冻结决议。

代码证据阶段必须从所选 API 的声明或定义文件出发，建立到可达实现的完整证据链，不能只阅读 API 主头文件：

- 在 `code-evidence.md` 覆盖全部成员、代码调用链、必查事实和代码缺口前，主代理和子代理只能读取 `manifest.json` 与目标代码链；不得打开、搜索、摘录或引用任一已提供资料。完成代码证据后，才能读取 `tasks/reconcile.md` 和资料文件。
- 基础编译中的全文搜索必须使用 `tools/ascendc-code-search.mjs`，并指定阅读清单或直接调用链给出的代码路径；它会排除文档、输出、测试、Markdown 和清单中全部已提供资料。不得以“全仓搜索”或无排除条件的搜索替代它。
- 使用 `tools/ascendc-code-reading-plan.mjs --relation-plan <temporary-api-relation-plan.json>` 生成临时代码阅读清单，复用资料收集前的调用关系定位结果，列出精确原型、候选代码闭包、参数传播、调用示例位置、公开注释候选和受限搜索边界。`semanticLinks.scannedFileCount` 只是自动索引数；必须在 `code-evidence.md` 逐项记录 `codeClosure.candidateFiles` 与公开注释候选的核验结果，阅读清单不能替代代码事实。
- 阅读 `semanticLinks.callCandidateDiagnostics`：底层同名函数只有在芯片条件、调用方式、参数类别和参数个数都与当前调用相符时，才能沿调用链继续核验。`ambiguous`、`no_compatible_candidate` 或 `unresolved_scoped_member` 表示不能安全确定，不得任选一个实现、不得把它当成代码事实；后者表示类型别名、对象或指针成员调用，尤其不能按裸函数名连接到同名全局实现。按 `tasks/evidence.md` 记录原因并形成代码缺口或定向回读。`resolved_overload_family` 中的重载都须按实际适用类型分别核验，不能写成唯一重载的结论。
- 以清单中的代码入口文件为起点，先用完整 `#include` 索引定位实现、类型、校验和宏；只有当前成员的声明、可达实现、已定位调用、实际关联宏、直接类型/约束或直接提及当前成员的文件进入 `codeClosure.candidateFiles` 并逐项核验。完整索引、定向搜索未命中和示例工程支撑文件不得混入该闭包；同名但调用方式不同的声明不能自行合并。
- 必须按 `tasks/evidence.md` 扫描产品支持、原型、参数、结构体/枚举、约束、调用链、输出状态和示例。调用示例先使用阅读清单中经核验的 `examples/` 结果（先 `Compute()`，再 `Process()`）；仅在脚本已定位 Helper 直接调用却未关联入口时，按 `tasks/example-call-chain.md` 在候选文件内受限核验调用链。两者都没有可用结果时，才按 `tasks/reconcile.md` 检查同 API 资料并最后构造。代码事实必须保留成员、重载、产品和条件的精确适用范围。
- 存在可独立阅读范围时，优先使用运行环境提供的子代理工具；每个代码文件或可分离片段只由一名深读责任方负责，主代理只回读冲突、缺失定位或无法判断的最小片段。并发任务必须同批发出；若运行环境串行返回，按串行返回记录。工具不可用、代码闭包极小或范围不可拆分时，可由主代理直接阅读并在 code-evidence.md 中记录原因。

### 资料触发的代码回查

资料陈述首先只是待核对候选。进入逐条事实对齐前，必须按 `tasks/reconcile.md` 判断每份已提供资料与当前 API 的关系，并将结论持久写回 `manifest.json`。当前 API 资料及混合资料中明确属于当前 API 的章节形成 R-ID；同类 API 资料只可作为调用示例结构参考；代码可达的下层 API 资料形成 D-ID，并逐条判断当前 API 是否实际使用其行为。下层资料不能因“调用了该 API”自动写入当前 API 文档；代码无法确认时必须用 `question` 让用户确认或暂缓。资料关系不清时也必须先用 `question` 确认，再提取事实。若对齐时发现具体事实已被一份或多份可用资料提到、但 `code-evidence.md` 尚无对应代码事实，必须先回到目标 API 的直接代码链，按 `tasks/evidence.md` 对该事实定向核验；不能因为首轮没有记录它就直接让用户选择。

- 回查证实后，将新代码事实追加到 `code-evidence.md`，再进行对齐；资料与代码一致时无需制造冲突。
- 回查发现不一致、适用范围不同或代码仍无法证实，才进入 `tasks/reconcile.md` 的确认流程。
- 回查只扩展到解释该事实所必需的直接代码链；相近 API 的调用至多是间接线索，不能单独证明当前 API 的参数单位、范围或逐值行为。

### 用户确认关口

冲突确认优先使用运行环境的 `question` 或等价结构化提问工具，展示具体候选并记录用户的明确选择。

- 每个独立冲突或待保留的未证实资料事实是一道问题：给出 ID、候选事实、来源定位和推荐项。每个资料候选必须写明资料名称、文件名、完整路径和定位；不得笼统称为“资料”。
- 实际冲突的选项对应实际候选；多份资料共同陈述、但代码未证实的事实只询问是否保留该共同事实或暂缓，不能要求用户在相同表述的来源之间任选。必须保留 `Other / 自行输入` 入口。
- 用户自定义内容先归一为一条原子事实，再用第二道 `question` 明确确认归一后的最终表述；不得擅自解释为某个候选。
- 新补证影响已确认事实时，必须生成“需二次确认”问题；不得静默以代码或资料覆盖用户决定。运行环境没有 `question` 工具时，用原生结构化提问或普通对话取得同等明确的回答并记录；未取得必需确认前停在该关口。

`resolution.md` 必须记录最终确认的具体事实、决策方式、候选证据、时间，以及作出决定时所依据的 API、代码和每份资料，而不只是“采用某来源”。

### 生成门禁

只有在 `tasks/supplement.md` 写完逐槽位覆盖记录后，才可冻结 `resolution.md`。最终化会检查没有未完成资料、未解决冲突、待确认资料事实和未完成覆盖项，并确认 API、代码和所有已提供资料仍对应本次任务。`【待开发补齐】` 是用户明确暂缓的可见结论，不是模型可自行填补的空位。

生成前预检：将审阅通过的正文写入最终命名文件后，先以最终化工具的 --check 模式完成只读预检；仅预检通过后才运行不带 --check 的最终化。有效的模板调用或其他代码形态若被校验器误拒，必须报告工具问题，不能靠添加说明性注释或无关包装代码规避校验。

调用覆盖检查按每个 C/C++ 代码块识别成员调用表达式；仅有声明、定义、注释、字符串或未求值的类型查询不构成调用示例。不跨代码块拼接语法。该检查不展开宏、不解析类型和重载，也不证明示例可编译或会执行；运算符表达式是否绑定当前成员、参数及行为是否正确，仍须结合本次源码证据审阅。

- [官方术语来源](references/official-sources.md)：需要核对术语时查阅对应版本，记录实际来源和适用范围。
- `references/cross_dir_tracking.md`：遇到跨目录 include 或实现追踪时读取；自动索引仍须结合当前代码核验。
- `references/architecture-context.md`：确有需要时读取的架构资料使用范围，不作为 API 行为或产品支持证据。

唯一会话创建入口为 `tools/ascendc-create-manifest.mjs`；插件选择和直接指定接口均通过该入口，最终由 `tools/ascendc-finalize.mjs` 校验。

使用示例见 [使用说明](references/usage.md)。命令路径均相对于本模块根目录。

生成与审阅最终文档前，必须读取 [产品名称与标签规范](references/product-document-format.md)，按当前产品名称、无序支持列表和全文差异化标签要求执行。

仅需单独定位完整文档格式问题时，可使用 [只读诊断](references/document-checks.md)；它不用于强制迁移父 Skill 的局部修订。
