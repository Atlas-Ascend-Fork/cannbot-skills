# 编译验证与测试用例补充

仅在源码已修改，或用户明确要求验证现有实现时执行本流程。纯扫描、分析和评审不自动触发耗时构建，也不新增测试文件。

## 1. 确定最小构建边界

1. 先读取仓库已有构建说明、`CMakeLists.txt`、`CMakePresets.json`和构建脚本，不自行发明另一套构建入口。
2. 从修改文件反查所属CMake target、算子包或插件；记录target、架构、SoC、CANN版本和关键编译选项。
3. 优先复用已有构建目录和工具链，只编译受影响target。默认不清理整个构建目录，也不执行全仓重编译。
4. 修改公共头、公共错误码宏或注册表时，再扩大到直接依赖target；只有公共ABI或公共模板变化才考虑更大范围构建。
5. 审计器无法确定同名`log.h`来源时，从真实编译命令提取`-I/-isystem/-D`，必要时使用编译器预处理或include trace验证。静态推断与编译器结果冲突时，以目标target的真实编译结果为准。

## 2. 编译执行与判定

按仓库已有方式执行，常见形式包括：

```bash
cmake --build <build_dir> --target <target> --parallel <jobs>
```

或者仓库提供的算子构建脚本。不要因为示例存在就跳过仓库说明直接套用命令。

编译验证至少记录：

| 字段 | 内容 |
|---|---|
| 构建入口 | 实际脚本或命令 |
| 受影响target | 修改文件对应target及扩展依赖 |
| 环境 | 架构、SoC、CANN路径/版本、编译器 |
| 结果 | 通过、失败或环境阻塞 |
| 证据 | 首个有效错误、相关日志路径和退出码 |

通过条件：修改文件及其直接依赖target编译成功，没有由本次错误码替换引入的未声明宏、参数数量/类型不匹配、头文件冲突或链接错误。

若因缺少工具链、设备、依赖包或权限无法构建，保留拟执行命令和首个阻塞证据，报告为“未验证”，不得写成“通过”。修复一次明确的环境配置问题后可重试；同类环境错误重复出现时停止无效重试。

## 3. 测试用例选择

先查找同算子、同模块和同测试框架的现有用例。优先扩展已有测试文件及fixture，不为单个错误码另建重复测试框架。

按“不同根因与不同上报路由”补用例，不按调用点数量机械增加：

| 整改类别 | 最小负向场景 | 必须断言 |
|---|---|---|
| shape/rank/size | 一个违反实际约束的输入 | 返回值、正式码、参数名、actual、expected/reason |
| dtype/format/value/list | 一个不支持值或组合 | 返回值、正式码、支持集合或范围、修复动作 |
| 必选输入为空 | 必选tensor或指针为空 | 正式空指针/缺失输入语义；不得产生内部E*9*** |
| InferShape/Tiling失败 | 合法输入下构造真实失败条件 | EZ1014或EZ1008、callee/rc/tiling key等诊断字段 |
| SoC/kernel不支持 | 当前实现确实没有匹配kernel的组合 | EZ1009、actual/supported SoC及选择条件 |
| 下层Runtime/ACL失败 | 使用现有mock/fault injection触发下层失败 | 下层正式首错存在；外层只补PLOG且不重复上报 |
| 删除不可达检查 | 覆盖正常构造路径；异常由公共边界测试承接 | 行为和公开errno不回归，无新增内部码 |

同一根因有多处相同宏替换时，选择一个代表用例验证错误码模板，再用现有参数化机制覆盖关键边界；不要为每个源代码调用点复制测试。

## 4. 测试层级与执行顺序

1. 先运行最接近改动的UT或host侧测试。
2. 需要ErrorManager实际输出时，运行已有日志捕获或集成测试。
3. 只有涉及op_kernel、Runtime、设备故障或真实Tiling执行时，才运行需要NPU的ST。
4. 最小测试通过后，运行仓库已有的相关测试集合；默认不扩展为全仓测试。

测试断言必须同时覆盖：

- 公开API返回值或兼容errno；
- 实际ErrorManager错误码；
- `opName/参数名/actual/expected/reason/rc`中该错误码要求的字段；
- 同一故障只有一个正式首错；
- 外层不存在额外EZ9999、EZ9903或其他重复内部码。

只断言“返回失败”或只搜索源码字符串，不能证明错误码整改正确。

## 5. 测试文件修改边界

- 用户要求整改时，可补充完成该整改所必需的测试；保留测试目录现有组织、命名和断言风格。
- 不修改与本次错误码路径无关的测试，不顺手扩大覆盖范围。
- 如果目标仓没有可复用测试框架，先在报告中给出最小测试设计和建议落点；创建新框架会显著扩大范围时，先征得用户确认。
- 需要设备、私有数据或不可用mock才能构造的故障，明确记录未覆盖原因和可执行的后续命令，不伪造测试结果。

## 6. Markdown报告内容

最终报告增加“编译验证”和“测试用例”两个章节：

### 编译验证

- target与构建命令；
- CANN/编译器/SoC环境；
- 通过、失败或未验证；
- 首个有效失败原因与未覆盖依赖。

### 测试用例

- 新增或修改的测试文件；
- 场景、输入、预期错误码和关键字段；
- 实际执行命令与结果；
- 首错唯一性检查；
- 未执行用例及原因。

只有静态审计、最小受影响构建、适用测试和负向日志断言均完成，最终“是否可关闭”才可填写“是”。

## 7. Skill脚本回归

当变更`scripts/error_code_triggers.py`、候选扫描器或审计器本身时，除算子构建与负向测试外，还要运行：

```bash
python scripts/test_error_code_trigger_coverage.py
```

入口族新增或映射规则变化时必须同步扩充测试，不允许只修改一个扫描脚本。
