# 文件检视场景（轻量流程）

## 触发
检视 DSL 算子、审核代码、代码审查、帮我检视 xxx、检查有没有问题、
复核算子实现

---

## 编排

### 阶段1：并行派发双规则线检视子 Agent

Read `steps/clause-review.md` 获取 prompt 模板，每个算子文件派发
**2 个**检视子 Agent（`subagent_type: "Explore"`，只读代码，文本返回
结构化发现），单消息并行，传入：

- 算子文件路径（多文件/目录输入时每个文件各派 2 个，单消息并行）
- 方法论路径：`core/methodology.md`
- 可读性规则线子 Agent：prompt 中 `{规则线}` 填 `可读性规则线`，
  `{规则文档}` 填 `references/readability-rules.md`
- 生产执行约束线子 Agent：prompt 中 `{规则线}` 填 `生产执行约束线`，
  `{规则文档}` 填 `references/execution-rules.md`

可读性线按十条原则的识别规程逐一检测，按置信度打分举证、判定；
执行约束线沿公开入口的真实调用链核查 DSL-E01~E06，确认违反直接
FAIL，依赖设备或动态证据的条目输出待验证。两线各自返回 YAML
结构化发现。

### 阶段2：撰写报告

合并两线结构化发现，按 `steps/report-write.md` 输出
`./{算子名}_review_report.md`。

**撰写要求（三原则：清晰、可读、简洁）**：

- **一个小标题一条发现**：标题装规则 ID、级别、位置三要素；正文
  固定骨架"问题一两句 → 证据 → 修复"，全文除 YAML 附录外零表格
- **结论先行**：开头 2-3 句话说清什么问题最多、集中在哪、建议的
  整改优先级——读者看完结论就知道要不要继续往下读
- **分组按判定语义**：生产执行约束（FAIL 在前）→ 可读性
  （high → medium → low）；编号全文连续
- **证据克制**：可读性线证据链一行压缩；执行约束线给调用链四要素；
  片段非必要不给（≤6 行原文，带行号前缀）
- **待验证/待确认写清缺什么**："缺什么证据、初判倾向"或"需要作者
  确认什么"，不写成 FAIL
- **不写元信息**：检视过程、规则介绍、统计口径说明都不写——读者
  是算子作者，不是技能用户
- **全零也出报告**：结论写"未发现可读性问题"，执行部分写检查范围
  及证据缺口

---

## 约束

- 严格按阶段顺序执行；子 Agent 必须实际 Read 算子代码，禁止仅凭规则
  文档示例下结论
- 每个 FAIL 必须引用真实行号和最短足以证明的代码片段（≤6 行）
- 待确认是一等结论，禁止为凑结论强行判 FAIL
