# 检视报告格式

报告写入调用方指定的位置；文件名由调用方安排。

**组织形式：一个小标题一条发现，全文除 YAML 附录外零表格。**
每条发现自包含——标题装核心要素，正文固定骨架，读者按需逐条看。

---

```markdown
# {算子名} CANNbot DSL 代码检视报告

- 文件：{路径}（{行数} 行）　日期：{YYYY-MM-DD}
{PR 模式}- PR：{链接}　merge_base：{commit}

## 结论

{2-3 句：什么问题最多、集中在哪、最该先改什么。}

生产执行约束：{N FAIL / M 待验证，说明源码检查与设备证据各自的范围}；
可读性：{结论}。

---

## 撰写要求

- 标题一行装核心三要素：`{编号}. {规则 ID} {规则名} · {级别} · {位置}`；
  正文不重复标题已有信息。文件检视位置写 `:行号`，PR 检视写
  `文件相对路径:行号`。问题编号全文连续（跨分组），便于互相引用
- 每条正文固定骨架：**问题一两句 → 证据 → 修复**。执行约束线的证据
  = 调用链、触发、副作用、回归四要素；可读性线的证据 = 一行压缩
  证据链，末尾 `→ 置信度%`
- 片段非必要不给：仅"一句话说不清、必须看代码才懂"的问题在问题句后
  附最短原文片段（≤6 行，带行号前缀，原文禁止改写）
- 分组按判定语义：生产执行约束（FAIL 在前，待验证不进本组）→
  可读性（high → medium → low → 行号）。疑似条目在级别后标
  `（疑似）`
- 待验证写"缺什么证据、初判倾向"，不写成 FAIL；待确认写"需要作者
  确认什么"，不是罗列问题
- 结论先行：生产执行约束与可读性两行计数摘要；执行约束线说明"源码
  检查通过"与"设备证据已验证"的边界，不能以没有采集到记录证明没有
  设备任务
- 全零也出报告：结论写"未发现可读性问题"，执行部分写检查范围及
  证据缺口，不把未验证写成通过
- 不写检视过程、规则介绍、统计口径说明等元信息——读者是算子作者，
  不是技能用户
- 全文禁止表格；YAML 附录保留供机读消费方使用
