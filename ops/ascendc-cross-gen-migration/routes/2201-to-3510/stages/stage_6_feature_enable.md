# 阶段 6：A5 新特性使能（有界尝试 / 可回退 / 基线对比）

**前置条件**：`[GATE-5] PERF=COLLECTED` 已输出（Stage 5 的基线数据是本阶段唯一对比基准）。

> **★ 本阶段为必做**（不是可选的性能优化阶段）。`2201→2002` 路线的 stage 6（`stage_6_optimize.md`）是 owner 指令触发的可选优化循环，与本阶段同号但**语义不同**，禁止据此把本阶段视为可选。

**本阶段解决什么问题**：迁移（Stage 0–4）保证的是**正确性**，默认沿用 A2 数据通路与编程模型。950 新增的数据通路与执行能力（L0C→UB 直通、UB→L1、SSBuffer、Mutex、双主模式等）在迁移门禁中**不会被自动启用**——不主动使能，交付物就是"A2 写法在 950 上跑"，性能通常显著低于硬件能力（实测案例：KFC MIX matmul 类算子保留 GM workspace 往返，AIC MTE2 占比 34%、cube_util 仅 37%）。

本阶段的作用：**对每个适用特性做一次有界尝试**——成功则保留（需三项证据），失败则在预算内回退并如实记录。**目标是把"没试过"变成"试过且知道结论"，而不是保证每个特性都成功。**

## Step 6.1：生成候选清单（a5_feature_plan.md）

以 Stage 1 的扫描信号、Stage 5 的瓶颈指标、算子代码形态为输入，从 `references/a5-feature-catalog.md` 逐项判定**适用 / 不适用**，写入 `${OP_DIR}/docs/a5_feature_plan.md`。

每项 MUST 记录：

| 字段 | 内容 |
|------|------|
| 特性名 |  Catalog 中的条目名 |
| 适用判定 | 适用 / 不适用 |
| 适用证据 | 代码位置（文件:行号）或 Stage 5 瓶颈指标（如 `AIC MTE2 ratio 34%`、`cube_util 37%`） |
| 预期收益 | 可量化的预期（如"消除 256KB/tile GM 往返"、"AIC MTE2 占比下降"） |
| **收益上限（数值 + 算式）** | **必填**：该特性理论最大收益占总耗时的上限，附算式与来源（实测占比 / 容量 / 指令次数）。用于 R1 判定是否允许跳过 |
| 验收指标 | 本特性的通过判据（见 Step 6.2 的 A/B 口径） |
| **知识真源** | **必填（适用项）**：Catalog 该条目「知识真源」列列出的文件。**开始尝试前 MUST 读取并在尝试记录中引用（文件 + 小节）**；只看速览表（l2-guide 速览等）不开真源 = 未完成前置 |
| 回退方式 | 备份位置 / git 范围 |

**不适用项也必须写明理由**（如"算子为纯 Vector，不涉及 L0C"）——"不适用"是结论，不是省略。

**排序原则**：按"预期收益 / 实现风险"降序排列；依赖关系明确时先做前置特性（如先 L0C→UB 再在其上做 UB 侧流水优化）。

### ★ R1：跳过的唯一合法情形（先判定，再排序）

只有两种情形允许"不尝试"：

| 情形 | 判据 | 记录要求 |
|------|------|---------|
| **A：已尝试且失败** | 实际改过代码、跑过验收三连（或至少编译+精度），到点回退 | 起止时间、构建循环数、报错原文、已排除假设 |
| **B：收益上限 < 保留门槛 5%** | `收益上限` 字段给出**可复核算式**且结果 < 5% | 算式 + 数据来源（如"转置仅占端到端 3.0%（同 shape tb=1 vs tb=0 实测）→ 上限 3% < 5%"） |

**除上述两种情形外，所有"适用"项 MUST 进入尝试队列。**

### ★ R2：实施难度不是阻断理由

以下理由**一律不构成跳过**，它们描述的是"尝试要做什么"，不是"做不到"：

- "需要先降 baseM / baseN / 缩小 tile"
- "需要改数据通路 / 改 C 的输出位置 / 需要重构向量侧"
- "需要先满足某个前置条件"
- "风险较大 / 收益不确定"

遇到这些情况，**前置改动本身就是尝试的一部分**：先做前置改动，再按 6.2.3 跑验收三连，6.2.4 的 A/B 必须测**净值**（含前置改动的代价）。只有"改完实测不达标"才算尝试失败。

**容量类约束的边界**：容量算式只能否决某个**具体变体**（如"整块驻留"），不能否决特性本身——同一特性往往存在流式/分块变体。写"容量不足"时必须同时评估分块变体，或说明该特性只有一种变体。

## Step 6.2：逐项尝试（一次只开一个特性）

### 6.2.1 隔离与备份（先做，再改代码）

- 优先用独立 git 分支或 worktree；工程非 git 仓库时，备份到 `${OP_DIR}/.a5-feature-attempt/backup_<feature>/`
- **同一时间只允许一个特性处于"已修改"状态**——多个特性混在一起时，性能变化无法归因，失败也无法界定责任

### 6.2.2 时间盒（硬约束）

**R3 预算分级**（从该特性**首次改代码**起算；读文档、分析、写计划**不计入**）：

| 档位 | 墙钟 | 构建-调试循环 | 适用条件 |
|------|------|--------------|---------|
| 默认 | **≤ 60 分钟** | **≤ 5 次** | 一般特性 |
| **主瓶颈** | **≤ 120 分钟** | **≤ 10 次** | 该特性消除的是 Stage 5 **已实测的主导成本**（如"每 tile 256KB 的 GM 写+读"、"占端到端 >30% 的某条流水"），须在计划中引用具体指标 |

每次"改代码 → 重新编译安装 → 复测"计 1 次循环（纯编译错误的修复也计入）。

**两者任一先到即停止该特性**。到点不允许"再试一下"、不允许开"顺手也改一下"的并行改动——超时即按 Step 6.3 回退。

> 判据说明：时间盒是**决策边界**，不是质量指标。到点仍未通过 → 回退并记录卡点，这属于 R1 情形 A（已尝试失败），是合法结论；**但"没开始"不属于任何合法情形**（R2）。

### 6.2.3 验收三连（缺一不可，全为实测证据）

| # | 验收项 | 要求 | 证据 |
|---|-------|------|------|
| ① | 编译安装 | `[GATE-3]` 同标准：BUILD=PASS INSTALL=PASS | 构建日志 + 安装验证输出 |
| ② | 精度全量复跑 | **Stage 4 的同一套用例全量重跑，N_PASS == N_TESTS** | pytest 输出（禁止只跑子集、禁止改阈值、禁止删用例） |
| ③ | 性能 A/B | 同 case 集合、同 profiler 配置（Level1 + PipeUtilization + L2Cache，warmup=5/active=5），对比 Stage 5 基线 | 前后 op_statistic.csv 的 per-step 耗时 |

**★ 新特性改变的是数据通路/同步协议，精度必须全量复跑**——只回归"改动涉及的 shape"不足以证明正确性（通路变化影响所有 shape）。

### 6.2.4 保留判据

保留须**同时**满足下列四组条件：

1. **编译安装 PASS**（验收①）；
2. **精度全量 N/N PASS**（验收②）；
3. **性能达标**（验收③）——满足下列**任一**即可：
   - a) 同一 case 集合的 per-step 中位耗时改善 ≥ 5%；或
   - b) Catalog 中该特性指定的瓶颈指标达标（如 `AIC MTE2 ratio` 相对下降 ≥ 10%、`cube_util` 绝对值提升 ≥ 5 个百分点）；
4. **A/B 测的是净值**——前置改动（缩小 base 块、改 tiling、调整 UB 布局等）的代价 MUST 计入同一组对比；只测"特性局部变快"而不含前置代价，不算通过（R2）。

> **与 R1 情形 B 的区别**：R1-B 用于**尝试前**按"收益上限"决定是否值得花预算；本条用于**尝试后**按"实测值"决定是否保留。两者作用于不同时点，可同时对同一特性成立（如上限 <5% 故不尝试；或尝试后实测 <5% 故回退），不构成矛盾。

**改善 < 5% 且未命中瓶颈指标 → 不保留**：把无收益的复杂度留在主干，会在后续维护中变成技术债；回退并在报告中记为"使能成功但收益不足"（与"调试失败"区分开）。

### 6.2.5 记录

每个特性结束后立即写入 `a5_feature_plan.md`：

- 结论（保留 / 回退-调试失败 / 回退-收益不足）
- **依据知识源（必填）**：实现与修复动作引用了哪些知识文件的哪些小节（如 `api-mapping.md §2.2 StoreDist 表`、`regbase_api_reference.md CastTrait 条目`）。**调试中产生的每个"未验证怀疑点"必须先回知识真源查证**——真源能解答而未查、任由预算耗尽的，记为流程缺陷而非纯技术失败
- Δ耗时、瓶颈指标前后值、耗时（分钟）、构建循环次数
- 失败卡点（错误码 / 报错原文 / 已排除的假设 / 查过的知识位置）

## Step 6.3：回退流程（放弃特性时 MUST 完整执行）

1. 恢复到该特性修改前的代码状态——MUST **精确到该特性改过的文件**：`git checkout -- <文件列表>` 或覆盖 `.a5_feature-attempt/` 备份，**确认这些文件的 diff 为空**。**禁止**裸 `git checkout .` / `git checkout -- .` / `git reset --hard`（基线未提交时会连带丢弃整个 Stage 2 迁移成果，且被误判为"回退成功"）；若基线尚未提交，尝试前 MUST 先 `git stash create` 或整目录备份并在记录中写明路径；
2. 重新编译安装（不得沿用失败版本的二进制）；
3. 复测一个代表性 case，确认**耗时回到基线水平**（排除残留的编译选项/宏定义/CMake 改动）；
4. 在 `a5_feature_plan.md` 记录卡点，并检查 CMake 选项、编译宏、tiling 结构体字段是否有未被代码回退覆盖的残留改动（这三类最容易漏）。

**禁止**：保留"半成品"代码（编译通过但未过精度）、用注释/宏开关把失败路径藏起来而不记录、把失败特性留在主干后再跑后续特性。

|------|:---:|------|----------|------------------|-----------|---------|------------|
| L0C→UB 直通（C 放 VECIN） | 是 | 保留 | -23.4% | AIC MTE2 34%→17% | 45 | 3 | — |

## Gate 输出条件

- [ ] **`${OP_DIR}/docs/a5_feature_plan.md` 存在**（路径与文件名固定，审查按此路径取），头部含「知识加载记录」（本阶段 LOADED + 每个已尝试特性的真源引用落盘）；Catalog 每个条目都有"适用/不适用"判定与证据
- [ ] 每个已尝试特性的记录含**「依据知识源」（文件 + 小节）**；调试怀疑点已回真源查证或明确记录"真源未覆盖"
- [ ] 每个**适用**特性必须二选一，不允许第三种状态：
      - **已尝试**：记录起止时间、构建循环次数、结论（保留 / 回退-调试失败 / 回退-收益不足）；
      - **未尝试**：**仅当收益上限 < 5% 且附可复核算式**（R1 情形 B）才允许。**"时间不足""实施难度大""需降 tile""需重构""风险较大"均不构成理由**（R2）。
- [ ] **收益上限 ≥5% 的适用特性均已实际改过代码**并跑过验收三连；只做分析未改代码 = Gate 不通过
- [ ] 前置改动（若特性需要）已计入同一 A/B 的净值对比，未只测局部收益
- [ ] 每个保留特性都有编译 PASS + 精度 N/N PASS + A/B 性能数据三项证据
- [ ] 每个回退特性都已执行 Step 6.3 回退四步并留下复测证据
- [ ] 最终代码状态 = 基线 + 已保留特性（无半成品、无残留宏/CMake 改动）
- [ ] 报告已追加「A5 新特性使能结果」章节

**全部通过 → 输出 `[GATE-6] A5_FEATURES=ENABLED k/N`**（k = 保留数，N = 适用特性数；k 可为 0，但"适用数为 0"必须有逐项不适用理由）→ 进入交付。

## 禁止行为

| 禁止 | 应该做 |
|------|--------|
| 无时间盒地长调试某个新特性 | 60 分钟 / 5 次构建循环到点即回退，记录卡点 |
| 为保留特性而只跑精度子集、放宽阈值、删用例 | 全量复跑 N_PASS == N_TESTS，否则回退 |
| 多个特性同时改，事后一次性测 | 一次一个特性，逐个 A/B 归因 |
| 收益 < 5% 仍保留（"反正没坏处"） | 回退并记为"收益不足"，保持主干简洁 |
| 回退只改代码，不恢复 CMake 选项/编译宏/tiling 字段 | 按 Step 6.3 四步完整回退并复测基线 |
| 用"已知限制"跳过某个适用特性 | 实际尝试并记录结论（成功 / 失败卡点），未尝试不算结论 |
| 以"时间不足""实施难度大""需降 tile""需重构""风险较大"为由跳过适用特性 | 只有"已尝试失败"或"收益上限<5%（附算式）"才可跳过（R1）；难度是尝试内容，不是理由（R2） |
| 用容量算式否决整个特性 | 容量只否决具体变体；须同时评估流式/分块变体，或证明该特性仅有一种变体 |
| 只测特性局部收益就宣称改善 | A/B 必须含前置改动代价，测净值（R2） |
| 把 Stage 6 记录写在任意 notes 文件里 | 固定写入 `${OP_DIR}/docs/a5_feature_plan.md`（Gate 按此路径核对） |
